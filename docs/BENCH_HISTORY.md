## 4. PIN=0/PIN=1 专家常驻分流同口径性能测试(2026-10-14)

> 目的:验证「热点专家入住 VRAM + GPU 辅助解码 + CPU 计算掩盖延迟」的解码加速在
> **README 0.2.7 同数据集**上是否成立。用户裁定口径见 §4.1。

### 4.1 协议(用户裁定,与 0.2.7 对齐)
* **数据集 = README 的 4 条互异 ~9.3k token DSH 转录**(`f_r11/f_r13/f_r20/f_r32`,
  `f_p1/f_p2`, `f_c4`)—— ⛔ **不是**上一会话自造的"同一条转录复制 1/2/4 份"
  (那份的首 token 在"空格 vs EOS"上是刀刃,见 EXPERIMENTS **B407**)。
* **聚合口径 = Σ输出token ÷ Σ解码窗口**(总产出/总时间)⇒ ⛔ **禁止"单流×C"**;
  ×C 只作对照列。**PREFIX_CACHE=0**(排除 prefix-cache 干扰)+ 形状预热 + 每档 ≥8 请求。
* 引擎:8070,GPU1,2,TP=2,dspark k=5,`max_num_seqs=4`,`MBT=8192`,
  `cudagraph_mode=FULL_DECODE_ONLY`,`enforce_eager=False`,greedy,`max_tokens=1024` 仅上限。

### 4.2 三臂结果(每臂一次独立 boot + 重启链;PE 与 APC 状态用 `/proc/<pid>/environ` 直读验证)
| 臂 | 钉选表 | 每层槽 | 逐层 period(ms) c1/c2/c4 | 口径A(墙钟聚合) c1/c2/c4 | 每请求中位 c1/c2/c4 |
|---|---|---|---|---|---|
| B = PIN=0 | — | — | 2.02 / 3.82 / 4.67 | 49.0 / 54.1 / 55.7 | 45.2 / 30.9 / 19.8 |
| A = PIN=1 | v0(342 条,命中≈22%) | 8.3 | — | 52.5 / 53.8 / 58.1 | 50.0 / 29.3 / 21.4 |
| C = PIN=1 | v1_700(700 条,命中≈32%) | 17.5 | **1.97 / 3.51 / 4.09** | 46.8 / 50.4 / 57.8 | 43.6 / 31.3 / 20.4 |

> CD_TIMING 行为独立 boot 的 D1(PIN=0)/D2(PIN=1+v1_700)专测,`XIAOTU_CD_TIMING=1`;
> 每格 = 同 (qlen,k) 分档的**逐层中位数**,样本 n=1142/1162(c1)、180/798(c4)。

### 4.3 机制结论(⭐ 本批的主结果)
1. **PIN=1 确实降低了物理步时**:逐层 period **c1 2.02→1.97ms(−2.5%)、c2 3.82→3.51(−8.1%)、
   c4 4.67→4.09(−12.4%)**;同期接受长度 AL **不变**(cdt 3.47→3.53)⇒ 该降幅应等效折算为
   tok/s。**降幅随并发增大**,因为 CPU MoE 占步时比例从 48%(c1)升到 62%(c4)。
2. **但 c1 的可赢空间本来就小**:`compare` 列里 compute 有 **~0.5ms/层的固定成分**
   (EP 归约 + 调用开销,与 topk 对数无关):qlen=6 时 0.97ms 里只有 ~0.47ms 是"可被
   分流省掉"的边际部分 ⇒ 即便命中 100%,c1 的步时上限也只有 ~+7%;命中 32% ⇒ **~2.5%**
   —— 正好等于实测值。**"12.5ms/step / −15%"的设计定价把固定部分也算进了可省项,系统性高估。**
3. **端到端 tok/s 被"轨迹混沌"淹掉**:c1 的 ±10% 样本噪声 ≫ 2.5% 的真实效应;
   c4 因效应较大(−12.4%)才在 tok/s 上露头(中位 19.8→20.4~23.0,取决于是否含自然结束样本)。
4. **按 README 的 ×C 对照列**(0.2.7 原口径):PIN=0 45.2/61.8/79.2、PIN=1(v1_700)
   43.6/62.6/81.6 ⇒ **c4 反超而 c1 持平偏下**,**未达成"全面优于 README"**
   (README 48.7/70.4/95.2)。c1 的 −10% 里有 −7% 是 **冷协议自身**(见 §4.4)。

### 4.4 与 README 现值的口径差(必须一起读)
* README 0.2.7 的 48.7/70.4/95.2 = **APC 开启(warm)+ 每请求解码段 × C**;
  本批按用户令 **APC=0(cold)+ 墙钟 Σtok/Σtime** ⇒ **两处口径差**。
* 冷协议下每轮都要为 4 条 ~9.3k token 的 prompt 付全量冷预填,而 `MBT=8192` 的分块预填
  **会饿死解码**(引擎自证:`prompt 933 tok/s` 同时 `generation 0.1 tok/s`)⇒
  c≥2 的墙钟窗口被预填占掉一大块。**该现象与 PIN 无关,era 码同样存在**(EXPERIMENTS **B407**)。
* ⇒ 结论:**README 不动**(数字未达标,且两口径不可直接比较);
  若要真正对齐 0.2.7,需另做一次 **APC 默认开启**的 warm 臂(本批未做,已记入待办)。

### 5.1 判据(与上表同源)
1. **物理步时(轨迹无关,判据首选)**:`XIAOTU_CD_TIMING` 逐层中位数
   **PIN=0 → PIN=1(v1_700):c1 2.02→1.97ms(−2.5%)、c2 3.82→3.51(−8.1%)、c4 4.67→4.09(−12.4%)**;
   同期接受长度 AL 无退化 ⇒ **PIN=1 是真实的步时优化,且并发越高越明显**(CPU MoE 占步时 48%→62%)。
2. **端到端 tok/s**:**只有 c4 两套口径 + 两种协议同向**(暖 +17.2%、冷 +16.3%)⇒ 可复现的胜档。
   c1/c2 的四组口径互相打架(见 EXPERIMENTS **B409** ③:AL 的 boot 间漂移 ±8~17% > 效应本身),
   ⇒ **c1 的 tok/s 不足以判 PIN**,不能用它宣布"全面优于/不优于"。
3. **对 README 的答案**:**不是"全面优于"**。PIN=1(v1_700)在暖协议下
   **c2 高 16.0%、c4 高 2.8%**,而 **c1 低 6.2%**;PIN=0 暖协议下 **c1 高 10.0%**、c4 低 12.3%。
   ⇒ **c4 是 PIN=1 的稳定胜档;c1 上 PIN 不是必需项**(步时虽优,但被 AL 噪声抵消)。

### 5.2 本次修掉的缺陷(都在 EXPERIMENTS **B407/B408/B409**)
* **钉选表尺寸**:v0 只有 **342 条**(每层 1~15 槽),而内存上限 ≈683 槽/rank(~9.0MB/槽);
  按真实路由流重生成 **v1_700**(诚实 split-half 命中 22%→**32.0%**,池 ≈5.85GiB/rank)。
* **`expert_pool.load_pin_table` 头偏移 16**(实际 `struct.calcsize("<4sIIII")`=20)
  ⇒ 原先少最后 1 条 + 多 1 条垃圾键;已修并在 docstring 写明唯一真源。
* **路由转储钩子不在在跑的 .so 里**(`cd-timing` 有、`xtu-rdump` 无;`.so` mtime 10-04~08 < `binding.cpp` 10-13)
  ⇒ `PLAN_EXPERT_RESIDENT` §6 的"已在生产 .so"**对当前树不成立**;要抓路由流必须先重编扩展。
* **两处口径/仪器伪影**(与 PIN 无关,均已结案):
  * 4.54/6.45s "停顿" = `MBT=8192` 分块预填**饿死解码**(era 同形);
  * "EOS@1 冷刀刃" = 上一会话**自造数据集**(同一条转录复制 1/2/4 份)的首 token 刀刃。

### 5.3 结论与建议
* **README 暂不换格**:没有"全面优于"的证据(见 5.1.3)。
* **若要换格**,唯一有依据的候选 = **c4 行换成 PIN=1 + v1_700**(两种协议同向,暖 98.8 / 冷 92.1 vs 现值 95.2);
  c1/c2 行维持现值。**该决定留给用户。**
* **下一步把 c1 做实**的唯一杠杆 = **Phase B(LRU 换入环)**:`expert_pool.swap_in()` 现为 `NotImplementedError`;
  静态表在内存上限只有 ~32%,而 LRU@683 实测 39.6%、base-50% 形状 48.0% ⇒ 命中率还能再上 ~8~16pp。
* **另一条更大的腿**:`compute` 里有 **~0.5ms/层固定成分**(EP 归约 + 调用开销),c1 占 48%;
  压它对 PIN=0/1 **都**有效,量级大于 PIN 本身。

### 6.5 ⛔ 两条**必须随数字一起读**的警告
1. **绝对 tok/s 含轨迹运气**:优化改变数值 ⇒ 两臂文本分岔 ⇒ 步数(=N/AL)不同 ⇒
   *固定长度只固定了分子*;**本版起必须与步时并列报**(B418)。
2. **TPOT 不是轨迹无关量**:`TPOT = 步时 ÷ AL`;实测 PIN=1 的 TPOT **反而 +9.0%** 而步时 −1.6%(差因就是 AL)。
   ⇒ **判"引擎更快"以步时为主**,并优先配对设计 + 分层标准化(`scripts/bench_standardize.py`)。

### 6.6 为什么"每层 −8.9%"到端到端只剩 −1.7%（2026-10-28 静态分析 + 实测）

**实测**：官方口径 C=1（`--conc 1 --n 1` × 16 轮，2 轮预热丢弃）
步时 **80.3 ms**（16 轮中位数的中位数，79.0–80.7）；对照 §6.2 N=1024 PIN=0 C=1 **81.7 ms** ⇒ **−1.7%**。

**静态分析（可算，不必猜）**：

| 项 | 来源 | 值 |
|---|---|---|
| 预取作用域 | `moe_v2_packed4_base.inc:629-634` 只 `_mm_prefetch` 专家权重行 | 仅 CPU MoE |
| 单层同步路径总时 | `binding.cpp` §582 注释实测（qlen=1） | **1.05 ms/层** |
| 其中引擎段（CPU MoE） | 同上 | **0.44 ms/层** |
| 非引擎段（D2H/H2D/host 交接） | 1.05 − 0.44 | 0.61 ms/层 |
| MoE 占步时 | 0.44×40 / 80.3 | **≈22%** |
| 预取对步时的净影响 | 8.9% × 22% | **≈−2.0%** |
| 实测净影响 | 80.3 vs 81.7 | **−1.7%** ✓ 吻合 |

⇒ **预取没有失效，是它的天花板只有 2%**：C=1、15K 上下文时步时大头是"每层串行交接 + GPU attention"，
不是 MoE 算术。**杠杆位置决定了收益量级**：
- 预取 = 让 CPU 算快一点（占 22%）⇒ 最多 −2%；
- Deferral = 让 CPU 与 GPU 不再排队（占 78% 那部分）⇒ 理论 −38%。

⚠️ **`XIAOTU_MOE_PF_DIST` 是编译期宏**（`#ifndef` + `#define 8`，**代码里没有 getenv**）
⇒ 想 A/B 预取必须**另编一个 `-DXIAOTU_MOE_PF_DIST=0` 变体**；用 env 设 0 是**空操作** ✗（2026-10-28 踩过）。

### 6.7 步时三段分解：CPU MoE 与 GPU 各占一半（2026-10-29 实测）

**口径**：ds41f、TP=2、60 线程/rank、官方 15K 载荷、C=1、`--tokenizer`、2 轮预热丢弃。

| 配置 | 步时 | 说明 |
|---|---:|---|
| 正常（`XIAOTU_MOE_ASYNC=0`） | **80.3 ms** | 5 轮：80.1 / 80.3 / 80.3 / 80.5 / 80.6 |
| `XIAOTU_MOE_FAKE_CPU=1`（不算 MoE，其余不变） | **40.4 ms** | 9 轮：40.3–40.5 |

⇒ **CPU MoE+EP ≈ 39.9 ms（49.7%）；GPU attention + 拷贝 + 派发 ≈ 40.4 ms（50.3%）**。

**交叉验证**：离线 harness（CPU-only，`BS=1 REP=5`，60 线程）给出 **0.42 ms/层**（×40=16.8 ms）；
服务内 `qlen≈6`（DSpark 每步多 token），早前 `qlen=6` 探针为 0.57–0.92 ms/层（×40=23–37 ms），
故服务端 1.0 ms/层、合计 39.9 ms 落在合理上包络内。三者单调自洽。

**推论（对优化方向的判据）**：
1. 只优化 MoE 内核（如预取 −8.9%/层）最多带来 `8.9% × 50% ≈ 4.4%` 的端到端收益
   —— 与 6.6 节实测的 −1.7% 同向但更乐观，说明预取在服务里还有未吃到的部分；
2. **唯一能拿到 30% 以上收益的方向是让 CPU MoE 与 GPU attention 重叠**（Expert Deferral），
   其理想上界 = `max(39.9, 40.4) ≈ 41 ms`，即 **−49%**；
3. 现实折价（线程抢核、PCIe 争用、握手往返）后预期 **−35% ~ −45%**。

⛔ `XIAOTU_MOE_FAKE_ALL=1` 会导致 `EngineDeadError`，**不可用于步时标定**；
`FAKE_CPU` 下输出为垃圾、请求会提前结束，必须用"满窗口轮"交叉核对（本次 9 轮含 1 轮 1023 token，值一致）。

### 6.8 编译器升级（GCC 11 → 16）：离线 −9.6%，**端到端无收益**（2026-10-29）

**背景**：构建脚本默认 `CXX=g++`，远端 `PATH` 里是 **GCC 11.4**；机器上另有 `g++-14`、`g++-16`。

**离线结果**（`ab_cpu_decode_offline.sh`，`BS=6`，同负载交错 A/B）：

| 轮 | GCC 11 | GCC 16 | 变化 |
|---|---:|---:|---:|
| r1 | 1.14 ms/层 | 1.05 | −7.9% |
| r2 | 1.16 ms/层 | 1.03 | −11.2% |
| 均值 | 1.15 | 1.04 | **−9.6%** |

两轮 `.so` 输出 **sha 逐字节相同**（`6578c321f50ce481…`）⇒ 无数值风险。

**服务级权威口径**（15K 载荷、C=1、`--tokenizer`、2 轮预热丢弃）：

| 臂 | 5 轮步时（ms） | 中位 |
|---|---|---:|
| 基线（GCC 11） | 80.1 / 80.3 / 80.3 / 80.5 / 80.6 | 80.3 |
| **GCC 16** | 80.2 / 80.2 / 80.1 / 80.1 / 79.8 | **80.1** |

⇒ **端到端 −0.2%，即无收益**。离线的 −9.6% 没有传导到服务。

**为什么**（可检验的解释，非结论）：离线是**单进程 60 线程**；服务是**两 rank × 60 = 120 线程**
且与 GPU attention 争用同一条内存通道。在服务那种争用状态下，CPU MoE 的瓶颈从"指令效率"
转为"内存延迟/争用"，编译器优化被吃掉。⚠️ 该解释未单独验证（需单进程 120 线程的对照）。

**处置**：构建脚本仍保留"自动优先 g++-16"，因为它**零风险且离线确实更快**（对纯 CPU 场景有效），
但**不要把它的收益算进服务口径**。

### 6.9 已否决方向清单（2026-10-29，含实测依据）

| 方向 | 否决依据 |
|---|---|
| 跨层 Expert Deferral | 串行依赖链 `attn(L)→MoE(L)→残差→attn(L+1)`，延后一层即算错（`PLAN_DEFERRAL_SEQ_PROTOCOL` §10） |
| 线程数上调/下调 | 4/CCD≈5/CCD，满核更慢（用户实测 + 本日确认） |
| 编译器 GCC11→16 | 端到端 −0.2%（本节） |
| 大页 THP | 稀疏跨度 ⇒ 3–5× 内存膨胀 + 单 node OOM，且实测更慢（`moe_v2.hpp:1700`） |
| UVA / mapped zero-copy | 历史失败实验 `d1ab48b`；用户多次实测均劣于双缓冲 |
| 降线程压 barrier | 依据被证伪（见 `USER_QA_LEDGER` #360/#362/#363） |

### 6.10 NUMA / 内存策略三臂对照：无可测收益（2026-10-30）

**口径**：ds41f、TP=2、60 线程/rank（全局 120）、官方 15K 载荷、C=1、`max_tokens=1024`、
`--tokenizer`、`MAXLEN=786432`。每臂 6 轮，**r1 因首请求仍在预填而系统性无效**（已记录），
取 r2–r6 中位数。

| 臂 | 分片内存策略（`numa_maps` 实测） | 线程 | 中位步时 | 相对 |
|---|---|---|---:|---:|
| A 默认 | `bind:0/1/2/3`（`MPOL_BIND` 单 node） | 无亲和 | **79.9 ms** | 基准 |
| B 交织 | `interleave:0-3`(rank0) / `interleave:4-7`(rank1) | 无亲和 | **80.7 ms** | **+1.0%** |
| C 亲和 | 同 A | `taskset -apc` → 各自 socket（0–95 / 96–191） | **80.45 ms** | **+0.75%** |

**证据强度**：三臂的分片策略与线程绑定均已用 `numa_maps` / `taskset` 实测证实生效，
**不是"env 没生效"**。

**结论**：
1. **`MPOL_INTERLEAVE` 到 socket 内 4 node 更慢**（+1.0%，两次独立测量同向 +1.0%/+1.3%）
   ⇒ 对流式、无复用的专家权重，**整块绑单 node 优于 node 内交织**；
2. **线程按 socket 亲和无收益**（+0.75%）。
   ⚠️ 该实验有 confound：只绑线程、非分片内存仍 `interleave:0-7` ⇒ 非分片访存跨域反而增加；
   "内存+线程同 socket"的彻底配置未测（启动脚本不支持按 rank 设 `membind`）；
3. ⇒ **NUMA/内存策略方向在本机没有可测收益**，三个配置全在 ±1% 内且都略慢。

**复现**：
```bash

# 策略证据
awk '$2 ~ /^bind:/{print $2}' /proc/<worker_pid>/numa_maps | sort | uniq -c
taskset -apc <cpu-list> <worker_pid>     # 必须 -a，否则只绑主线程
```

### 6.11 CPU MoE 的线程/预取空间：也无可拿收益（2026-10-30）

**问题**：CPU MoE 占步时 49.7%，若能提高达成带宽就是直接收益。

**实验一：线程扫描**（离线、真实形状 `DEDUP=12, BS=6`、真实权重、单进程）

| THREADS | 24 | 36 | 60 | 96 | 120 |
|---|---:|---:|---:|---:|---:|
| ms/层 | 2.05 | 2.03 | 1.22 | 1.08 | 0.99 |

五档 sha 全同（`6578c321…`）⇒ 纯调度效应。**60→120 可再快 19%**。

**但**：服务是 2 rank × 60 = **120 线程总量**，其每层 CPU 时间 **1.0 ms** ≈ 离线单进程
120 线程的 **0.99 ms** ⇒ **服务已处在最优点**，加线程只会加剧争用（与"满核更慢"实测一致）。

**实验二：PF_DIST 扫描 + 交错对照**（60 线程，编译期宏）

单次扫描看似 `PF=4` 快 9%（1.13 vs 1.24），但同轮内交错重复 3 轮后：

| 轮 | pf=4 | pf=8 |
|---|---:|---:|
| 1 | 1.07 | 1.05 |
| 2 | 1.10 | 1.04 |
| 3 | 1.06 | 1.04 |
| **中位** | 1.07 | **1.04** |

⇒ **现行默认 `PF_DIST=8` 反而快 2.8%**；单次扫描的 9% 是**时间漂移噪声**。方向关闭。

**结论**：CPU MoE 每层 ~1.0 ms 在**调度层面**已无可拿空间（线程数、预取距离都到顶）。
剩余只有"减少字节"（热专家 pin，实测命中 32% 时 −2.5%）与算法/量化。

**⚠️ 方法论（本轮最大教训）**：本轮**三次"看到收益"全部被更严格对照否定**
（NUMA 交织 +1.0%、PF=4 表面 −9%、每线程带宽 −21%）。
根因都是**单次测量 + 跨条件比较**。
⇒ 今后任何 ≥5% 结论：**同轮内交错重复 ≥3 次**，且固定"形状 / 字节口径 / 线程总量"。

**复现**：

### 6.11 ⭐ 15K 基准的载荷缺陷与修正（2026-10-31，用户裁定）

**背景**：`dsh_15k_v2.jsonl` 按固定 15K token 硬切窗口，切点常落在 `[assistant]` 句子中间
⇒ prompt 语义变成"接着把这段转录写下去"，没有自然结束点。表现为：

* 全部样本 `finish_reason=length`（被 cap 截断，`capped=100%`）；
* draft 每步全中 ⇒ `Mean acceptance length` 打满 **6.00**（= k+1 天花板）、`acceptance rate=100%`；
* decode 被放大成 **71–72 tok/s**（v2 的假快），而历史为 ≈40。

**修正**：新构造 `scripts/build_dsh15k_v3.py` —— 窗口端点**对齐到完整 `[user]` 回合**，
用 V4.1 官方编码渲染（结尾 `<｜Assistant｜><think>`），长度 10.5–13.2K，
并剔除"需要现场材料才能作答"的复审类条目（`dsh_15k_v3_selfcontained.jsonl`，5 条）。

**修正后实测**（ds41f / TP=2 / 实例 k3 / C=1 / 预热 2 条丢弃 / 每条 prompt 前插 400 随机字符破缓存）：

| 指标 | 值 | 对照历史 |
|---|---|---|
| prompt token 中位 | 11,873 | ≈15K 载荷同量级 |
| **纯 prefill** | **848 tok/s**（785–924） | 历史 ≈1.1K ✓ 同量级 |
| **TTFT 中位** | **14.0 s** | —— |
| **纯 decode 中位** | **41.7 tok/s** | 历史 ≈40 ✓ |
| **步时中位** | **78.5 ms/步** | 历史 79.9–80.6 ms ✓ |
| AL（≈每步 token） | **3.27** | 历史 ≈3 ✓（v2 是 6.00 ✗） |
| 实际输出长度中位 | 723 token（565–1024） | 自然结束 |
| 截断占比 | 1/3 = 33% | v2 是 100% |
| 失败 | 0 / 3 | —— |

**结论**：修正后的四项指标与历史基线**全部落在同一量级**，v2 的 26K prefill / 72 decode

### 6.12 C=1/2/4 三档实测（2026-10-31，v3 自包含载荷，实例 k3）

**口径**：ds41f / TP=2 / MAXSEQS=4 / MBT=8192 / GPU_UTIL=0.85；
载荷 `dsh_15k_v3_selfcontained.jsonl`（窗口对齐到完整 `[user]` 回合）；
每档先跑 **2×C 条预热并丢弃**；每条 prompt 前插 400 随机字符**破前缀缓存**（命中增量断言为 0）；
`max_tokens=1024` 仅作上限、允许自然结束；单流/双流/四流各自独立成批。

| C | 纯 prefill | TTFT 中位 | 每路 decode | **聚合 decode（C×每路）** | 步时中位 | AL | 失败 |
|---:|---:|---:|---:|---:|---:|---:|---:|
| 1 | 848 tok/s | 14.0 s | 41.7 | **41.7** | **78.5 ms** | 3.27 | 0/3 |
| 2 | 877 tok/s | 14.0 s | 24.0 | **48.0** | **130.9 ms** | 3.41 | 0/8 |
| 4 | 821 tok/s | 14.4 s | 11.8 | **47.3** | **285.6 ms** | 3.34 | 0/16 |

**结论（三条，均有数据支撑）**

1. ⭐ **步时是目前最稳的"引擎速度"量**：78.5 ms（C=1），比历史 79.9–80.6 ms **略好**，
   与"本版做了优化"一致；而 `tok/s` 的难看**不是引擎退化**。
2. ⭐ **tok/s 的差异由 AL 解释，不由步时解释**：
   历史 README 的 C=1 48.7 tok/s 对应 `AL = 48.7 × 0.080 ≈ 3.90`；
   本次 `AL = 3.27`、步时 78.5 ms ⇒ `3.27 ÷ 0.0785 = 41.7` ✓ 与实测完全吻合。
   ⇒ **AL 3.90 → 3.27（−16%）＋步时 −2% ⇒ tok/s 48.7 → 41.7（−14%）**，
   即：**投机解码"运气"不好，而不是引擎变慢**（与 2026-10-31 的推测一致）。
3. ⚠️ **聚合吞吐在 C≥2 后饱和在 ≈48 tok/s**：C=2 → 48.0、C=4 → 47.3，
   因为**步时随批量近似线性增长**（78.5 → 130.9 → 285.6 ms，C=4 是 C=1 的 3.64×），
   每路速率被同比例摊薄（41.7 → 24.0 → 11.8）。
   ⇒ 这与"CPU MoE 占解码一半"的既有结论自洽：**多路并发时 CPU 专家计算成倍增加，吃不到并行**。
   ⛔ 因此 README v0.2.7 的 48.7 / 70.4 / 95.2（APC 命中 warm、按"每请求解码段 × C"外推）
   **在当前载荷与实例上不可复现**；本表的聚合是实测每路 × C，并可用 `AL ÷ 步时` 交叉校验。

**测量陷阱留档**：曾把"同波最早首 token → 最晚末 token"当聚合分母，C=2 时该窗口包含第二路
**串行的 14 s 预填等待**，算出 30 tok/s（比每路 24 还接近），属**口径错误**——聚合必须用
`C × 每路` 或 `AL ÷ 步时`，不能把预填交错算进解码窗口。
