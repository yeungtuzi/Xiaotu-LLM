## 1. 方案简介

> 本节为对外定稿表述（2026-11-17），与介绍材料首屏文字一致，不再改写。

本方案采用自研 CPU 与 GPU 混合推理架构，实现了 PD 分离（预填充/解码分离）和分布式推理。
可使用半专业级显卡实现推理加速和现有云计算服务器进行集群推理，可支撑 DeepSeek-V4.1-Flash 官方模型。
对外提供统一推理入口，具备密钥管理、配额控制与按密钥计量能力，并可按需扩展规模。

## 2. 为什么单机有硬边界

以下都是本仓库实测（2026-09 口径，详见 `docs/BENCHMARKS.md` 与内部设计文档）：

| 量 | 实测值 | 对架构的含义 |
|---|---|---|
| 每 token 激活的专家权重 | **3.246 GB**（43 层） | 决定 MoE 侧的带宽需求 |
| 单机内存边际流式带宽 | **692–768 GB/s**（24 通道 DDR5） | 单机专家池的天花板 |
| 每层固定成本 | **≈0.124 ms/层**（与字节数、行数无关） | ⚠️ **不随节点数下降**，43 层串行是硬边界 |
| 纯 GPU 地板（注意力等，C=1） | **16.8 ms/token** | 注意力必须留在 GPU（延迟敏感 + 需 kernel） |
| 31 层 CPU MoE（C=1） | **7.4 ms/token** | CPU 侧确实能算 MoE |
| 单序列 KV（fp8_ds_mla，8K 上下文） | **≈0.196 MiB/token** | 长上下文下 KV 比权重更吃容量 |

结论：**单机能跑多快由「每层固定成本 × 层数」锁死**；要再往上只有两条路——更快的单机（纵向），或者把专家池和并发铺开到多机（横向）。本项目选后者。

## 3. 目标形态

| 维度 | 目标 |
|---|---|
| 计算节点 | 约 **1600 台纯 CPU 服务器**（MoE 解码 + KV 池宿主）|
| 加速节点 | 约 **160 台 8 卡 GPU 服务器**（注意力 / prefill）|
| 网络 | **100 GB/s 级 IB** |
| 对外入口 | **单一端口**，提供多个多模态模型（ds / glm / qwen 系列），实例数可后续调整 |
| 缓存 | **集群级 KV 池**：跨实例复用前缀，省掉重复 prefill |
| 可靠性 | 逐组件无单点（网关、KV 池、编排均有冗余）|
| 伸缩 | 远景按需自动启停实例 |

## 4. 角色分工

```
          ┌──────────── 单一入口（网关：鉴权 / 路由 / 计量）────────────┐
          │                                                          │
   ┌──────▼──────┐                                          ┌────────▼────────┐
   │  GPU 机群    │  注意力 + prefill（延迟敏感）             │  编排 / 自动伸缩 │
   │  8 卡 × N    │◀──────────── KV 池 ─────────────────────▶│                 │
   └──────┬──────┘                                          └─────────────────┘
          │ 每层归约（跨机，替代单机 /dev/shm）
   ┌──────▼──────────────────────────────────────────────────┐
   │  CPU 机群：MoE 解码（每 token 专家计算）+ KV 池宿主      │
   └─────────────────────────────────────────────────────────┘
```

* **GPU 侧**不做 MoE 专家计算，只做注意力、prefill、采样；
* **CPU 侧**承担每 token 的专家计算，并在空闲容量上托管 KV 池；
* 两者之间**唯一需要新写的部分**是「每层 MoE 归约」的跨机实现（单机版走 `/dev/shm`，实测 ~14 µs/层）。

## 7. 容量估算基准（2026-11-17）

> **基准模型：DeepSeek-V4.1-Flash-1017**（476 GB，官方 FP8 稠密 + FP4 专家；下称 ds41f-1017）。
> 本节所有吞吐数字若未特别说明，均指该模型；换模型必须重测，不能线性外推。

做规模换算时用以下三条基线。**前两条含估算成分**，对外承诺前必须用同协议实测替换。

| 维度 | 基准 | 性质 |
|---|---|---|
| prefill（每 GPU）| NVIDIA RTX PRO 6000D **≈2,000 tok/s**；MTT S5000 **≈600 tok/s**（实测 640）| 前者为估算基准，后者实测（2026-11-14）|
| decode（每节点）| 双路 EPYC 9004 **内存满配** ≈**100 tok/s/节点**；旧服务器按内存带宽比例折算 | 估算基准 |
| 网络 | **万兆以太网**为基准；支持 RDMA 时上下浮动，须按拓扑设计后实测 | 设计约束 |

### 7.1 换算公式

```
GPU 卡数   ≈ QPS × 平均输入长度  ÷ 单卡 prefill 吞吐   （RTX 6000D: 2000；S5000: 600）
CPU 节点数 ≈ QPS × 平均输出长度  ÷ 单节点 decode 吞吐  （基准 100，再按内存带宽打折）
```

**示例**（QPS=10、输入 8K、输出 500）：

| 侧 | 需求量 | 折合资源 |
|---|---|---|
| prefill | 80,000 tok/s | RTX 6000D **40 卡** / S5000 **≈134 卡** |
| decode | 5,000 tok/s | **≈50 个**双路 EPYC 9004 节点（旧机按带宽折算后更多）|

⇒ 这个形状下 **CPU 节点数与 GPU 卡数同量级**，正是存量 CPU 资产能直接变现的位置。

### 7.2 旧服务器怎么折算（只认带宽）

```
节点 decode 吞吐 ≈ 100 tok/s × (该机内存带宽 / EPYC 9004 满配带宽) × 网络效率系数
```

* MoE 解码是**权重字节流受限**，内存带宽是一阶因素；核数/主频不是主因；
* 无 RDMA 的万兆以太网取系数 <1.0，按实测校准。

### 7.3 一个必须先算清楚的网络约束

单 token KV ≈0.196 MiB（fp8_ds_mla，8K 上下文）⇒ 8K 上下文的 KV 约 **1.6 GiB**：

| 链路 | 传输 1.6 GiB 的纯时间 |
|---|---|
| 万兆以太网（≈1.25 GB/s）| **≈1.4 s** |
| 100 Gb/s（≈12.5 GB/s）| ≈0.13 s |

⇒ 在万兆上做 PD 分离，每个长上下文请求要多付约 1.4 s；**必须 RDMA / 25–100 GbE，或让 KV 与计算同机**。

---


### 7.4 P : D 配比是**不平衡**的（1 个 prefill 节点带 N 个 decode 节点）

早期设计就是「一台 GPU 前段带若干台 CPU decode 节点」——因为**旧服务器不值钱**，
decode 侧用存量设备堆比买 GPU 便宜一个数量级。但 **N 不是常数**：

存量机箱通常受供电与 PCIe 通道限制**塞不满 8 卡**，因此按 **4 卡 P 节点**估算：

```
D 节点数 / 每个 P 节点(4 卡) = 4 × 单卡 prefill × L_out ÷ (100 × L_in)
```

**关键口径：D 节点的总需求只由业务输出量决定**（`QPS × 输出长度 ÷ 单节点 decode`），**与 GPU 卡型无关**；
卡越强，单台 P 吞吐越大，能喂饱的 D 越多 ⇒ 单台 P 的配比更高，但**总节点数更少**。

算例（QPS=10、输入 8K、输出 500）：

| 方案 | GPU 卡数 | P 节点（4 卡/台）| D 节点（decode）| 合计节点 | 每台 P 配 D |
|---|---|---|---|---|---|
| **RTX PRO 6000D**（2,000 tok/s/卡）| 40 卡 | 10 台 | 50 台 | **60 台** | 1 : 5 |
| **MTT S5000**（600 tok/s/卡）| 134 卡 | 34 台 | 50 台 | **84 台** | 1 : 1.5 |

⇒ 更强卡的方案**总节点更少**；「每台 P 配更多 D」只是因为它一台顶三台多的 prefill 产出。
若输出拉长到 2K（8K/2K）：D 变 200 台，P 不变 ⇒ 合计 **210 / 234 台**。

⇒ **输出越长，decode 越长尾**：8K/2K 形状下 1 台 4 卡 P 要配 20 台 D，这正是存量 CPU 服务器最能发挥价值的场景。

代价也要一起算：每个请求的 KV（8K ≈1.6 GiB）必须搬到它对应的那台 D（万兆 ≈1.4 s），
且同一会话要落到持有其 KV 的那台节点 ⇒ 需要会话粘滞或 KV 池。


### 7.5 按吞吐需求反算（采购口径）

| 目标：prefill **100,000 tok/s** + decode **100,000 tok/s** | P 节点（4 卡/台）| GPU 卡数 | D 节点（decode）| 合计 |
|---|---|---|---|---|
| **RTX PRO 6000D**（2,000 tok/s/卡）| **13 台** | 52 卡 | **1,000 台** | **1,013 台** |
| **MTT S5000**（600 tok/s/卡）| **42 台** | 168 卡 | **1,000 台** | **1,042 台** |

⇒ **P 侧差 3.3 倍，D 侧完全相同**（D 只由 decode 目标决定）。
旧机按带宽折算会让 D 变多：系数 0.5 ⇒ D 2,000 台，合计 2,013 / 2,042 台。

## 8. 分阶段路线

| 阶段 | 内容 | 通过判据 |
|---|---|---|
| P0 | 单机多副本共享缓存 | 跨实例前缀命中 |
| P1 | 线程常驻策略标定 | 层间隔-成本曲线可解释 |
| P2 | **两机原型**：跨机每层归约 | 每层延迟 µs 级实测 |
| P3 | 引入 KV 池（Mooncake / NIXL 等）| 池命中后的 TTFT 与带宽实测 |
| P4 | 网关 + 编排 + 多网关 HA | 单端口多模型压测通过 |
| P5 | 专家池横向扩展 + 自动伸缩 | 按需启停、无单点演练 |

当前处于 **P0/P4 的交界**：单机缓存已通、网关已上线，跨机部分（P2/P3）尚未开始。

## 9. 尚未验证的清单（诚实版）

1. **跨机每层归约延迟**——集群方案里唯一必须新写的部分，尚无实测；
2. **KV 池的带宽与命中收益**——单机前缀缓存数据不能外推到集群；
3. **CPU 节点线程 park 策略**——单机实测调优可带来数十秒级差异，集群下需要重新标定；
4. **单点**——网关、KV 池、编排三处的冗余目前都只是设计，未做故障演练；
5. **国产卡一致性**——S5000 上的数值/算子覆盖仍在补（能力缺口逐条登记在内部台账）。
