# XTier 与 Xiaotu-LLM：架构对照，以及「32 GB 显存 + 无专家常驻」的速度归因

> 编制：Xiaotu-LLM 引擎作者
> 日期：2026-10-28
> 对照对象：`a775828b-dot/xtier`，`main` @ `edbca46`（2026-10-27 17:35 +0800），本地副本 `/root/lvllm/repos/xtier`
> 本文不预设结论；凡外部项目的数据均标注「其自报」，未在本机复现。

## 0. 结论摘要

1. **「不做任何专家常驻」这个前提不成立。** 该 32 GB 配置每层仍有 4 个热专家槽，并在 decode 期间借 prefill 的显存把槽位临时扩到最多 +27；此外 MTP 草稿的 3 层专家整层常驻显存。所谓「无常驻」只成立于「无整层常驻」这一层含义。
2. **该 32 GB 配置并不是「快」，而是「在 128 GiB 内存 + 32 GB 显存的硬上限下能跑」。** 其自报 decode 28.1–32.7 tok/s、prefill 1 155–1 186 tok/s，相对其自身 72 GB 配置分别是 22–27% 与 25–31%；对本引擎同模型口径（decode 68.6 tok/s、prefill 1 190 tok/s）则是 decode 约 0.45 倍、prefill 基本持平。
3. **真正比本引擎快一个档的是它的 72 GB 配置**（decode 141.8 tok/s、冷 prefill 3 812/4 768 tok/s、每验证步 31.7 ms）。差异主要来自四点：GPU 侧承担约 13% 槽位的专家（4-bit 权重常驻显存，W4A16）、单卡无 TP 归约、SM120 的原生 FP4/FP8 与配套内核、以及模型专用加速包（其中「按置信度截断验证」让被截掉的 token 直接跳过 CPU 专家，对 CPU 卸载型引擎是纯步时收益）。
4. **最值得本引擎吸收的不是它的速度，而是它的两处内存工程**：CUDA VMM 的「地址空间固定、只改映射」弹性槽（解码图指针永不变化），与「所有权 + 提交/发布」两阶段的换入协议。这两点正好对应本引擎 2026-10-27 事故的根因面（`empty_cache` 解映射在飞 kernel 的显存）。

## 2. 相同点（八条，机制级）

1. **同一个判断：专家按热度分层放置，按路由动态换入。** 两边都用「启动时按排名表装填 + 运行中按衰减计数换入换出」；XTier 用半衰期 50 次调用与最小增益 1.5，本项目用 `XIAOTU_PIN_WINDOW` / `_HYST` / `_MAXSWAP`。槽位数量级不同：本项目 700 槽（≈17.5 槽/层 × 40 层），XTier 的 DS 生产配置 50 槽/层。
2. **同一个执行模型：一层之内 GPU 与 CPU 并行算不相交的专家，结果相加。** XTier 的步时因此是 `max(GPU 部分, CPU 部分)` 而非两者之和；本项目 v0.2.8 起同构。
3. **同一类引擎与同一类优化**：AVX-512 BF16/VBMI 内核、NUMA 切片（每个 NUMA 节点只读本地分片）、每 token 只读「用到的专家」一次、fp4 权重解包用查表/位运算。
4. **同样的 prefill 思路**：长 prompt 分块，权重从锁页内存按块流式上传（本项目 `tile ring`，XTier 的 GPU 分组 GEMM + 锁页暂存），用 H2D 与计算重叠。
5. **同样的「不改宿主」约束与「加载后自证接管」**：XTier 明确「SGLang 会吞插件异常，故加载时校验后端确实接管，否则报错退出」；本项目同病同防（`mainline_shims` 的多处 `except` 静默即为此列出的已知风险）。
6. **同样的投机解码依赖**：两边都以 DSpark/MTP 的验证宽度 `m` 为单位设计内核（XTier `MAX_M=16`、DS 预设 `m=6`；本项目 MBT 8192 + DSpark k=5）。decode 吞吐都以「每验证步接受几个 token」为第一杠杆。
7. **同样的模型无关核心 + 模型专用加速包**：XTier `packs/<模块名>`，本项目按模型分支 + 单点 `GPU_DEVICE` 判定。
8. **同样的验收哲学**：逐元素/逐 token 对拍（XTier 的「照抄 0 错」、PPL 与「开/关两臂逐 token 比 logprob」；本项目的数值门禁与逐 token 对拍），都把「无异常」当作必要条件而非充分条件。

## 3. 差异（机制级，按影响排序）

| # | 维度 | XTier | 本引擎 | 对 decode 步时的影响 |
|---|---|---|---|---|
| 1 | 硬件代际 | SM120：原生 FP4/FP8 张量核，HBM3e | SM80（A100）：无 FP8/FP4 单元。专家在 CPU 侧走 **INT8 激活 × MXFP4**（`gk=32`+`e8m0` 由权重格式自动启用，VNNI 内核；fp4 码值含于 int8 ⇒ 权重侧逐位精确），GPU 侧 dense/attention 在无 FP8 硬件上反量化后计算 | 决定性：同一 GEMM，A100 无原生 FP8/FP4，算力与有效带宽差一档 |
| 2 | 并行度 | 单卡 TP=1 | TP=2（每层一次 TP 归约）+ 两卡按层切分 | 每层固定开销 |
| 3 | 驻留粒度 | **每层独立槽数**（DS 50 槽/层，Qwen 其余层 155 槽/层），另有「整层全常驻」层 | 全局热专家池 + **整层常驻**（Qwen 12 层精选）；PIN 默认关 | 覆盖的激活占比差一倍以上 |
| 4 | 槽位预算 | **规划器**（探测 GPU/CPU 每层耗时 × 路由档案 ⇒ 每层槽数，目标 `max(GPU,CPU)` 最小） | 手工/静态表（`XIAOTU_PIN_TABLE`、`XIAOTU_PIN_STATIC`） | 槽位可能给多或给少 |
| 5 | 显存弹性 | **CUDA VMM**：地址空间预留 S 槽，常驻只映射 `base`，prefill 期把其余解映射；解码图指针不变 | 定长缓冲 + 退休区（本轮刚修）；无 VMM 弹性 | prefill 显存与热专家槽不再互斥 |
| 6 | 冷数据层 | **NVMe 三级**：冷专家池（O_DIRECT、2.35 MB NUMA 分片、四盘并行、跨层预读）+ Engram/PLE 行放 NVMe（DS 的 189 GB） | **只有 DRAM 两级**；NVMe 仅是设计位（README 明示默认关、未实现） | 决定「能否在 128 GiB 内存里跑」 |
| 7 | KV | NVFP4/FP8 KV 池（Qwen 省下的显存换常驻层；MiniMax 512K 下 FP8 放不下） | CED 压缩 KV（5 437→2 106 B/token）+ FP8 | 显存预算的分配 |
| 8 | 验证截断 | 按草稿置信度截断验证，**被截掉的 token 跳过 CPU 专家** | 无截断（整宽验证） | CPU 卸载型引擎的直接步时收益 |
| 9 | 通信协议 | 写信箱（C++ 调度线程 + 映射命令环），**CUDA 可捕获**，驻留表在显存里随图重放读取 ⇒ 换入不需重捕获 | Python 侧调度 + 图捕获约束较多 | 每层几 µs 级，但对 40 层累积可见 |
| 10 | 加载 | 快速加载：专家直接从检查点/冷盘读进引擎，DS 472→186 s | 常规 safetensors 加载 | 不影响步时，影响迭代速度 |
| 11 | 平台覆盖 | CUDA only | CUDA + MUSA 同一份代码（`GPU_DEVICE` 门控） | 非性能项，属交付面差异 |
| 12 | 观测 | 启动台 + 规划器 + `mem_guard.sh` + 每会话明细 JSON | 心跳 `[xtu-pf-progress]`、`[xtu-vram]` 遥测、看门狗、压测套件 | 都可回溯，风格不同 |

三处需要展开的机制：

**(a) 槽位分配从「全局池」变成「每层预算」。** 因为步时是 `max(GPU,CPU)`，只要 GPU 侧还没成为瓶颈，**加槽就是免费的**；规划器据此把显存按层分配到「两侧同时算完」，剩余自由度再换成「整层常驻」（prefill 不必上传）。全局池无法表达「这一层多给、那一层少给」，这是本项目 `expert_pool` 的结构性缺口。

**(b) 弹性槽的本质是「地址空间固定、映射可变」。** `cuMemAddressReserve` 预留 2× 槽数的地址空间，常驻只映射 1×，prefill 需要的显存由未映射部分让出；释放时先暂停策略、提交一次 commit、等拷贝落地、把专家移出驻留表、再 `cuMemUnmap`。**解码图里记录的 arena 指针全程不变**，因此不需要重新捕获图。

**(c) 提交/发布两阶段。** 换入分成「发布新专家」与「驱逐旧专家」两个序号，且**先发布后驱逐**：已落地的新专家可能已被更晚的换入选为牺牲者，必须在本窗口结束时不在表内。这条规则解决的是「换入换出与图重放并发」的经典竞态——正是本项目本周反复出现的故障类别。

## 4. 「32 GB 显存 + 无专家常驻」为什么还能跑到 28–33 tok/s

### 4.1 先把三个前提纠正

| 说法 | 事实 |
|---|---|
| 「不做任何专家常驻」 | 每层 4 个热专家槽（40 层共约 160 个专家），decode 期弹性扩到最多 +27 槽/层；MTP 草稿的 3 层专家整层驻留显存。**「无整层常驻」成立，「无专家驻留」不成立。** |
| 「32 GB 显存」 | 容量是硬上限（占位 40 487 MiB 之外只留 31 999 MiB），但**卡仍是 72 GB 的 Blackwell**：带宽、FP4 单元、显存频率都没有被削。被削的是容量，不是速度。 |
| 「快」 | 相对其 72 GB 配置是 22–27%（decode）。相对本引擎 ds41f 口径（68.6 tok/s）是 0.45 倍。它快在「128 GiB 内存就能跑」，不快在「tok/s」。 |

### 4.2 其自报的账（`docs/reports/2026-10-27-ds41-minimal.md`）

```
配置：冷专家 70%（每层 384 个里内存只放 115 个，约 81 GiB）、热专家 4 槽/层 + 弹性（最多 +27，prefill 前还回）、
      prefill 分块 8K、上下文 128K、DSpark（草稿 3 层专家全在显存）、Engram 行缓存 2 GiB、CPU 112 线程、
      --mem-fraction-static 0.95
上限：显存 31 999 MiB（vram_limit.py 占位）、内存 128 GiB（MemoryMax=128G、MemorySwapMax=0）
实测：prefill 1 186 / 1 165 / 1 155 tok/s @32K/64K/128K；decode 28.5 / 28.1 / 32.7 tok/s
资源：不可回收内存 110.5 GiB（峰值）、显存 29.5 GB、冷启动 382–398 s、照抄 0 错
```

其自述的两个瓶颈：

- **prefill 卡在读盘**：8K 分块会路由到几乎所有专家，每块要把约 70%（约 202 GB）的专家从 4 块盘重读一遍；实测 4 盘合计约 18 GB/s（每盘 4.5–4.7 GB/s）。分块再大显存装不下（128K 上下文时 8K 分块的 prefill 已要约 5 GiB，因为 DS 的稀疏注意力索引器随上下文增大）。
- **decode 每步约 95–106 个冷专家缺失**（约 2 GB），读盘等待约 70 ms/步；DSpark 每步接受 3–4 个 token ⇒ 约 30 tok/s。

### 4.3 复算：这个 32 GB 配置的步时构成

用其公开参数就能把账对上，不需要假设：

| 项 | 量 | 计算 |
|---|---|---|
| 单专家字节 | 18.8 MB（TP=2 下每 rank 半片 9.0 MB） | MXFP4：`(2I·H/2 + H·I/2)` 加 scale，`H=5120 I=2304`；本项目引擎 banner 报 `I=1152` 是 rank 局部值 |
| 每步缺失 | 95–106 个 | 其报告 |
| 每步读盘字节 | 1.8–2.0 GB | 100 × 18.8 MB |
| 读盘时间 | 约 100–110 ms | @18 GB/s；其自报「等待约 70 ms」说明有相当部分与计算重叠 |
| 每验证步接受 | 3–4 token | DSpark |
| ⇒ 每步 | 约 130–150 ms | 28.5–32.7 tok/s × 3.5–4 token |
| ⇒ 每 token | 约 31–36 ms | 其中读盘占大头 |

**也就是说：这个配置的步时是「读盘时间 ÷ 每步接受数」。**「不做常驻」不是它的优点，而是它在 32 GB 里的**被迫选择**——128K KV 池、8K prefill 分块（约 5 GiB）、草稿层、索引器工作区已经把 32 GB 占满，容不下更多槽位。它把这部分自由度全花在「上下文」和「分块」上，代价就是每步多读约 2 GB 盘。

### 4.4 换算到同一口径：它并不比本引擎快

| 配置 | 显存 | 专家放置 | 每验证步 | 接受长度 | decode | prefill | 口径与日期 |
|---|---|---|---|---|---|---|---|
| 本引擎 2×A100 | 80 GB | 全部宿主内存（PIN off） | **81.3 ms**（v0.2.8 发行说明，C=1，PIN=0） | 未单独发布 | **68.6** | **1 190** | README v0.2.9（2026-10-22），15K prompt，C=1 |
| XTier 1×RTX PRO 5000 | 72 GB | 50 槽/层（13%）+ 其余内存 | **31.7 ms** | 4.50 | **141.8** | **3 812 / 4 768** | 其 README（2026-10-27），64K/500K 会话冷 prefill |
| XTier 最小化 | 32 GB | 4 槽/层 + 弹性 + 30% 内存 + 70% NVMe | 约 130–150 ms | 3–4 | **28.5–32.7** | **1 155–1 186** | 其报告（2026-10-27），32K/64K/128K |

三条免责声明必须同时成立才可引用此表：① 两边的 prefill 口径不同（15K 固定载荷 vs 会话首个请求的冷 prefill）；② 接受长度有随机性，权威比较看**每验证步**；③ 硬件不同代，任何「同口径快 X%」的说法都不成立，只能做**机制归因**。

另有一条口径缺口必须写明：**本项目没有「每验证步」这一指标**（仓库里只有 `step time` / TPOT / ITL 三种口径），上表第三列与 XTier 的「每验证步」不完全同义，只能作量级参考。

在这个前提下，只能给出三条**相对**结论（均不作同硬件定量拆分）：

- 本引擎 PIN 关闭（GPU 不承担任何专家）时 68.6 tok/s；XTier 在 GPU 只承担 4 槽/层、但 70% 专家在盘上时 28.5–32.7 tok/s。差别主要在「多少专家在盘上」，而不在「有没有常驻」。
- XTier 的 72 GB 配置（50 槽/层、专家全在内存）141.8 tok/s，约为本引擎的 2 倍；这部分由「GPU 承担的专家激活占比」与「硬件代际 + 模型专用内核」共同贡献，缺同硬件对照，不做定量拆分。
- **XTier 没有任何「GPU 零槽位」的配置**：它的官方 main 基线也是 50 槽/层。因此在「完全不常驻」这个点上，两边没有同口径数据，任何「它不常驻也比我们快」的说法都缺证据。

**结论：差距不在「有没有常驻」，而在「GPU 承担了多少专家激活」与「硬件代际」。**

### 4.5 真正快的那一档（72 GB）为什么快 2 倍

按贡献排序：

1. **GPU 承担了一部分专家，且 GPU 侧是 4-bit 常驻。** 50 槽/层 × 40 层 = 2 000 个专家、37.6 GB 显存；路由高度倾斜，被承担的**激活占比**显著高于 13% 的槽位占比。GPU 侧内核是 Triton 写的 W4A16（`_halves` 用 `cvt.rn.f16x2.e2m1x2` 内联汇编把 FP4 解成 FP16），权重以打包 4-bit 常驻，**不需要 FP8/FP4 张量核**——这也是它能在消费级 Blackwell 上跑得快的原因。
2. **步时是 `max(GPU, CPU)`。** 规划器按「两侧同时算完」分配每层槽数，多出来的显存再换整层常驻。本引擎的 PIN 是**全局池**且默认关，实测收益 C=1 81.3→79.8 ms（−1.9%）、C=2 113.2→108.2 ms（−4.4%）、C=4 188.1→160.8 ms（−14.5%），机制吻合（CPU MoE 占步时由 48% 升到 62%，挪走的权重越到高并发越关键）；但**覆盖不足**：诚实 split-half 口径下覆盖率 32%（700 槽 ≈ 17.5 槽/层 × 40 层，池 5.85–6.14 GiB/rank），社区配方的 82–90% 对应 155×23 量级的槽位，**从未在本机复现**。另需注意槽位口径：TP=2 下每槽只占 9.0 MB/rank，XTier 单卡每槽 18.8 MB，故「同样显存能放多少槽」对两边的含义不同。
3. **单卡无 TP 归约。** 本引擎每层一次 TP 归约，40 层累积是毫秒级固定开销。
4. **SM120 的算力/带宽与配套内核**：块 FP8 GEMM 调优配置（按 `N,K` 存 JSON）、MXFP8 走 FlashInfer CUTLASS、窄 decode 形状走 `b12x`、`wo_a` 存 FP8 并把 decode 走 Triton 分组 einsum、索引器 decode 走分页路径。其自报这些加速包相对官方 main 每步快 39%（50.9 → 31.2 ms）——**即同样硬件上，框架默认与本引擎的形态接近，差距主要来自这些内核级工作**。
5. **按置信度截断验证**：草稿置信度低的 token 不送去验证，**这些 token 的专家计算直接跳过**。对 CPU 卸载型引擎，这等于按概率减少每步的专家字节数。
6. **显存预算的再分配**：KV 走 NVFP4（Qwen 省下的显存换常驻层）、Engram 189 GB 的行放 NVMe、PLE 放 NVMe、prefill 残余显存在 decode 期借给热专家（弹性）。每一项都把「非专家」的显存挤出来给专家。

### 4.6 这个 32 GB 结果的适用边界

- **主机内存带宽是隐含前提。** 其本机 24 通道约 920 GB/s；其自估换 8 通道（约 200 GB/s）decode 约慢 10%。但**真实 RTX 5090 台式机是 2 通道（约 80–100 GB/s）**，此时 CPU 侧要算的那 30% 专家会主导步时，28–33 tok/s 的外推不成立。该报告在正文里明确写了这条，引用时不可省略。
- **盘是第二前提。** 四块 PCIe 4.0 盘合计 18 GB/s；其中一块无 DRAM 盘（FX700）持续满速读约 100 秒后塌到 0.06 GB/s，一次缺失要等最慢的盘，会拖住整个池子。其报告为此专门记录了复现。
- **容量是模拟出来的**，卡仍是 72 GB；显存带宽与 FP4 单元未被限制，故该实验回答的是「容量够不够」，不是「低端卡行不行」。

## 5. 可直接借鉴（按价值排序）

1. **CUDA VMM 的弹性槽（地址空间固定、映射可变）。** 对本引擎的直接价值不在性能，而在**正确性**：本周 illegal memory access 的根因链正是「`empty_cache` 让 `expandable_segments` 解映射了在飞 kernel 仍在访问的物理页」。用显式 VMM 管理「必须长期存在的缓冲（专家槽、tile 环、落地区）」，把这些缓冲**移出 torch 分配器**，从结构上消灭「释放-重映射」这一类竞态；解码图指针不变，也就不需要重捕获。
2. **提交/发布两阶段换入协议。** 「先发布落地的、后驱逐被替换的」，且驱逐序列号先于发布序列号。本引擎的 `plan_swap` 与 `_reuse_moe` 键空间问题（本轮的 `("inter", K)` 修复）属于同一族问题：**换入换出必须相对于「图重放」有一个明确的可观测提交点**。
3. **每层槽位预算 + 规划器。** 判据是 `max(GPU, CPU)`，只需一次探测（约 1–3 分钟合成权重）+ 一份路由档案，即可把显存按层分配。本引擎当前是全局池，且 PIN 默认关；若把「每层槽数」变成显存预算的下发结果，`XIAOTU_PIN` 的收益上限会明显提高。
4. **按置信度截断验证。** 与投机解码解耦、对输出分布无损（其自报「输出分布与不用投机解码相同」）。对 CPU 卸载型引擎，这是**唯一**能直接减少每步专家字节数的解码侧手段。
5. **冷专家池的读法约束**：2.35 MB 对齐的整片读、四盘并行、跨层预读、只按「衰减使用次数最低」选牺牲者、拷贝期锁槽。若本项目将来要支持「专家全量放不进内存」的机型，这份设计可直接复用；其中「盘要先做几分钟持续读测试」是必须继承的运维判据。
6. **大表行放 NVMe。** DS 的 Engram 189 GB、Qwen 的 PLE 48 GiB。本引擎**没有任何 NVMe 数据路径**（代码中 `nvme` 零命中，只有 README 的设计位）：Engram 以 45.78 GiB 的 pinned 宿主内存存在，PLE 以 23.8 GiB 的 `/dev/shm` 共享存在，`ple_offload.py` 走的是宿主 UVA/锁页。NVMe 行表可把整机内存需求再降一档，代价是长上下文的表查询延迟；其判据是「放傲腾时与锁页表持平」。

## 6. 不可照搬

1. **SM120 专属内核路径**（FP4 张量核、`b12x`、分页索引器、NVFP4 KV）。A100 是 SM80，没有 FP8/FP4 单元；这些优化在 A100 上要么不可用，要么退化为反量化。
2. **单卡 TP=1 的预算假设。** 本引擎是 TP=2，专家的宿主分片与显存预算按两卡切分；XTier 的槽位公式（每层 S 槽）无法直接搬到 TP=2 的 rank 局部预算上。
3. **SGLang 的钩子形态。** 其「包在 `FusedMoE` 量化方法外面」的接法与 vLLM 的 `RoutedExperts` 补丁栈不同，尤其 CUDA 图捕获路径的约束不同；照抄会把本引擎的图捕获问题重新打开。
4. **「生产不动」的迭代前提。** 它按「每个模型达标才切换」逐个模型迁移，本项目是单一主线、单份代码同时服务三个模型与两个平台（CUDA/MUSA），切换成本与回归面不可比。

## 7. 建议的下一步（含判据与成本）

| 序 | 动作 | 判据 | 成本 |
|---|---|---|---|
| 1 | 把专家槽/持久缓冲迁到显式 VMM（先只做「专家槽 + tile 环 + 落地缓冲」三处） | 连续 4 h 压测零 illegal access；解码图不重捕获；槽位增删不影响图 | 中（约 1–2 天，需重编译扩展） |
| 2 | 每层槽位预算：用一次探测 + 现有路由日志，产出 `XIAOTU_PIN_TABLE` 的每层槽数 | 同显存下每验证步不慢于手工配置；GPU 侧每层时间不超过 CPU 侧 | 低（离线计算，不需重启生产） |
| 3 | 截断验证：复现「置信度阈值 → 跳过的 token 数 → 步时」三段关系 | 输出分布与不截断逐 token 一致；步时随阈值单调下降 | 中（需一次受控窗口） |
| 4 | 评估 NVMe 行表（Engram/PLE） | 16K/64K prompt 的 TTFT 不劣于锁页内存；宿主 RSS 下降 ≥ 100 GiB | 高（新数据路径） |
| 5 | 槽位覆盖率的度量口径对齐「GPU 承担率」 | 报告里直接给「本步 GPU 承担的专家激活占比」 | 低（已有 `XIAOTU_PIN_HITSTAT` 基础） |

第 1、2 项不需要重启生产即可推进；第 3、4 项各需要一次受控窗口。

## 9. 遗留：本文引用到的本项目文档缺陷

写这份对照时发现三处，引用前需先修，否则同一份材料会出现两种说法：

1. **INT8 默认值自相矛盾。** `docs/INT8_ACTIVATION_FOR_MXFP4_EXPERTS.md:4` 写「总开关默认由权重格式决定」，同文件 `:78` 仍写「默认不启用、`XIAOTU_MOE_INT8=1` 才打开」；代码是前者（`mixed_experts.py:1387/1396/1410`，零 env 时 MXFP4+`gk=32`+`e8m0` ⇒ INT8=1）。过期的是 `:78` 那一段。
2. **32% 覆盖率可能被旧路由表污染。** `docs/EXPERIMENTS.md:34002` 记录「当前 PIN 表大概率是 0917 路由」。本文把它当作「本机诚实 split-half 口径」引用，若换用当前路由表重测，该数字可能变化；在重测之前，该数字只代表「旧表 + split-half」。
3. **社区配方（82–90%）在本仓库没有任何实测复现。** `dev-docs/EXPERT_RESIDENCY_REFERENCES.md:182-184` 的三条是待办。本文凡引用「社区 82–90%」均标注为**其原始出处、未在本机复现**，不可写成「已知可达」。

## 附：一句话回答「为什么它 32 GB 也能这么快」

因为它**并不是**在 32 GB 里「不做常驻还能快」，而是把「常驻」换成了「每步从 4 块 NVMe 并行读约 2 GB 冷专家」，再用 DSpark 每步接受 3–4 个 token 把这段读盘时间摊到每个 token 上；同时它仍保留了每层 4 个热专家槽、decode 期弹性加槽、草稿层整层驻留。它的真正优势有三条独立来源：**4-bit 专家（18.8 MB/个）让同样带宽能喂的专家数翻倍**、**每层 `max(GPU,CPU)` 的槽位规划**、**单卡 Blackwell 的原生 FP4 与配套内核**。前两条本引擎可以吸收，第三条受限于 A100 的 SM80 代际。
