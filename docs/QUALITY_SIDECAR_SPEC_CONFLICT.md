# 质量复盘：DSpark 投机解码 × GPU0 挎斗 不能同时开

> **结论**：在 ds41f-1017 上，**DSpark 投机解码（k=5）与 GPU0 挎斗同时启用会显著破坏输出质量**
> （工具调用参数畸形、正文为空、中英混杂、超长失控）。
> 二者**单独使用**时质量正常。当前生产 8700 选择 **spec on + 无挎斗**（质量优先）。

## 1. 背景

DSH 接入 8700 后反馈“模型变笨”：工具调用参数缺失（`missing required property "description"`）、
回复为空、思考/正文混杂。排查发现不是知识能力问题（同一模型单轮推理 9/10 正确）。

## 2. 可复现测试

- 测试夹具：把项目文档（README / AGENTS / ENV_TWO_MACHINES / BENCH_PROTOCOL / 复盘 / release notes）
  放进 workspace，要求模型用 bash/read/glob **自行阅读至少 4 个文件**后总结（≤400 字，以“等待指示”结尾）；
- 判分：10 个关键事实命中 ≥7 且结尾正确 ⇒ 通过；
- 每档 4~5 次，temperature=1.0、reasoning_effort=low（与 DSH 实际一致）。

## 3. 结果矩阵

| 配置 | 通过率 | 典型失败 |
|---|---|---|
| 投机解码 + 挎斗 | **1/5**（另 temp0: 2/3）| 工具调用标签畸形、空正文、超长失控 |
| 投机解码 + 无挎斗 | **5/5** | — |
| 无投机 + 挎斗 | **9/9**（temp0 4/4 + temp1 4/4 + 另一轮）| — |
| 投机（greedy draft）+ 挎斗 | 3/5 | 仍有空正文、16k 字失控 |

## 4. 结论与处置

- **挎斗与投机解码在 ds41f 上互斥**：挎斗加速的是“普通 decode”，而投机解码把 decode 变成
  “verify（多 token 前向）”，两者叠加时输出质量不可接受；
- **当前生产 8700**：`SPEC=1`（DSpark k=5）+ **无挎斗**，质量 5/5；
- 若要挎斗（C≥2 步时收益）：**必须 `SPEC=0`**，质量 9/9；
- 待办（未做）：定位挎斗在 verify 多 token 路径上的数值/时序问题（怀疑异步缓冲与多 token 复用），
  修好后才能同时启用。

## 5. 性能对照（15K 官方口径，热机）

| 配置 | C=1 tok/s | C=1 步时 | C=4 tok/s | C=4 步时 |
|---|---|---|---|---|
| A：spec on（k=5）+ 无挎斗 | **68.6** | 82 ms | **79.6** | 197 ms |
| B：spec off + 挎斗 | 11.6 | 86 ms | 61.4 | 60 ms |

- B 的步时更低，但**每步只出 1 个 token**，吞吐反而只有 A 的 1/6（C=1）与 3/4（C=4）；
- ⇒ 对 agent（C=1）场景，A 同时是**质量与速度**的最优解；
- 挎斗要重新可用，必须先修它在 verify 多 token 路径上的问题（见 §4 待办）。

## 6. 更严重的发现：挎斗在 batch>1（qlen>1）时输出异常

用**相同提示词 × N 并发**（temp=0，SPEC=0）对比单请求基准：

| 配置 | 单请求 | batch=4 输出长度 |
|---|---|---|
| 无挎斗（对照） | 119 | 121 / 129 / 125 / 119（全部完整、语义正确）|
| **有挎斗** | 118 | **0 / 153 / 0 / 33**（2 条空、1 条截断）|
| 有挎斗（batch=2） | 120 | 72 / 115（均明显短于单请求）|

⇒ **挎斗在 qlen>1 时不可用**：batch 解码会得到空回复/截断/异常内容。
这也意味着 v0.3.0 里 C≥2 的挎斗吞吐数据（106.8 / 110.2 tok/s）是在**输出已损坏**的情况下测得的，
该功能目前**只能用于单请求（qlen=1）**，不能作为 C≥2 的生产特性。

待查方向：`pin_hidden/ids/weights` 在 qlen>1 时的布局与 worker 读取、以及 host_begin/host_end
的合并是否按 token 下标正确对齐（qlen=1 时二者退化相同，所以单请求正常）。

## 7. 缺陷定位：问题在「命中路径」，不是基础设施

用**零命中表**（保留表头、掩码全 0）重启同一套挎斗环境，再跑 batch=4：

| 表 | batch=4 输出长度 |
|---|---|
| 正常表（1900 槽）| **0 / 153 / 0 / 33**（空/截断）|
| 零命中表（不触发挎斗）| 122 / 126 / 126 / 110（全部完整、语义正确）|

⇒ 挎斗的加载、显存、通信、worker 都正常；**只要真正发生命中（CPU 权重被置 0 + worker 回填），
qlen>1 时结果就错**。定位范围缩小到：

1. `host_begin` 里按 token 的 `ids/wts` 下标与 worker 的 `(t = p // K)` 对齐；
2. `host_end` 里 `side_out[qlen*hidden]` 到 CPU `out` 的合并；
3. 命中项在 CPU 侧被置 0 后，worker 是否**逐 token** 都回填了对应专家。

（qlen=1 时上述下标退化相同，所以单请求永远正确。）

## 8. 修复尝试与结论（2026-10-24 凌晨）

**根因确认**：ds41f 的挎斗走的是 **MXFP4 N-major GEMV**（`use_fp8=False`），该内核**只对 qlen=1 成立**；
原代码在 `qlen>1` 时直接 `out_host.zero_()`（fail-closed），但 C++ `host_begin` 已经把这批 token
的 CPU 专家权重置 0 ⇒ **命中专家被静默丢弃**，batch>1 输出异常。

**尝试修复**：把 MXFP4 分支改成逐 token 循环（每个 token 单独 GEMV 后回填）。
- 正确性：batch=4 全部恢复正常（127/118/120/120），spec+挎斗的 agent 测试 **9/10**；
- 性能：**C=1 只有 9.9 tok/s（步时 317 ms）**，比无挎斗的 68.6 慢 7 倍——逐 token 串行把并行度吃光了。

**最终处置**：
- 保留一条**安全护栏**（`sidecar.py`）：MXFP4 时把 `max_qlen` 限制为 1，
  `qlen>1` 直接放弃挎斗（不置 0 CPU 权重）⇒ 不再产生错误输出，也不再拖慢 batch；
- **生产 8700 仍用 A（spec on + 无挎斗）**；
- 挎斗若要真正支持 batch，需要实现**多 token 批量的 N-major 内核**（不是循环），属于新的内核工作。

## 9. 批量 N-major 内核原型（2026-10-24 上午）：正确但不可用

按 fp8 内核的思路给 MXFP4 N-major 加了 `forward_batch`（x 按 token 索引、`_wsum` 按 token 聚合、
pad slot 权重 0），并把 `sidecar_gpu0` 的 qlen>1 分支接上。

- 正确性：batch=4 输出全部完整（119~121 字），与无挎斗一致 ✅
- 性能：**C=1 实测 1.6~5 tok/s**（BN=4 时约 5，BN=128 时约 1.6），
  无挎斗基线 68.6 ⇒ **慢 14~40 倍** ❌

原因：N-major 是“每 slot 一次 GEMV”的形状，qlen×topk 个 slot（C=4 时 24 个）叠上
`_gateup` 的 4608 列 × 20 段权重加载，单层耗时 ~4ms，43 层就把一步吃掉数百 ms；
它本来就是为 qlen=1、少量命中 slot 设计的，不适合批量。

**结论**：要在 batch 上真正用挎斗，需要**另写一个以 token 为 M 的 MXFP4 GEMM 内核**
（类似 fp8 的 `gpu_moe_decode_fp8` 的 tiling），而不是把 GEMV 循环/批量拼起来。
在此之前：MXFP4 挎斗仅在 qlen=1 启用（`sidecar.py` 护栏），生产保持 A。
