# GPU0 挎斗项目复盘（2026-10-24）

> ⛔ **已撤回（2026-10-24）**：v0.3.0 的挎斗（辅助 GPU）功能已撤回，不再提供、不再承诺性能。
> 本文件保留作为历史记录，但其中的性能数据（如 C=2/4 的 106.8 / 110.2 tok/s）是
> “命中专家被静默丢弃”这个 bug 造成的错误结果，**不可引用**。
> 修正后的实测：C=1/2/4 全部**慢于**无挎斗基线（C=4：122.6 ms vs 74.6 ms），
> 完整证据见 [`docs/QUALITY_SIDECAR_SPEC_CONFLICT.md`](QUALITY_SIDECAR_SPEC_CONFLICT.md) §1–§14。


> **定性：一次很有益的失败。**
> 机制全部打通、数值正确、端到端可跑；但在 A100 上性能不成立，
> 收益（省下的 CPU offload / 换来的 KV）小于跨设备逐层边界的代价。

---

## 0. 一句话结论

| 对象 | 结论 |
|---|---|
| **qfn NVFP4（A 方案）** | 机制正确（单层 0.37–0.52%，全 48 层 needle 正确），但**净负**：同配置 5.9 vs 12.3 tok/s；根因是每层 **8.6–11.3 ms** 的跨设备开销 |
| **ds41f 15K（挎斗 1900 槽）** | C≥2 有小幅正收益（C4 36.4 vs 24.0 tok/s），C=1 与基线同量级（15.2 vs 13.2）；绝对值仍远低于 README（42.6/69.7/72.0） |
| **建议** | qfn 不用 GPU0 挎斗；ds41f 仅在 C≥2 可考虑；长上下文/高吞吐走 sm120/96GB 换卡 |

---

## 1. 目标

1. 用第三张卡（GPU0）分担 MoE，让 qfn NVFP4（68GB 专家）在 2×A100 上
   去掉 1GB CPU offload、把 KV 从 0.41GB 提到 ~15GB；
2. GPU0 撤除时回退纯 GPU1/2 + CPU 兜底，同一请求 needle 一致；
3. 对 ds41f：量化挎斗在 15K 上下文、C=1/2/4 下的真实收益。

---

## 2. 设计

### 2.1 qfn（A 方案：每层 40% 专家放 GPU0）

- GPU0 持有每层 **40%（206/512）专家**的原始 NVFP4 布局（Marlin 重排之前）；
- GPU1/2 的 Marlin 照常计算其余 60%；
- 每层路由后，把归 GPU0 的命中专家的 topk 权重**置零**再交给 Marlin，
  GPU0 用已验证的 NVFP4 内核（E2M1 + E4M3 g16 + `weight_scale_2`）计算这些命中，
  按原路由权重并回；
- 共享专家（bf16）完全不动。

### 2.2 ds41f（CPU + GPU0 混合）

- 插件原有 CPU MoE 引擎 + GPU1/2 的 PIN 热专家；
- `XTU_SIDECAR=gpu0` + `expert_pin_sidecar_1900.bin`：GPU0 再常驻 1900 个热专家，
  与 CPU、GPU1/2 并行计算。

| 组件 | 内容 |

| 回退 | `QFN_A_LAYER` 未设 / `XTU_SIDECAR` 未设 ⇒ 零行为变化 |

## 4. 测试结果

### 4.1 qfn NVFP4 数值（全部通过）

| 阶段 | 结果 |
|---|---|
| P0 离线（真实 layer0 权重 + 引擎 dump 的 x/ids/out） | 相对误差 **0.3–0.5%** |
| P1 单层（TP=1，40% 置零 + 并回 vs 全量 Marlin） | **0.004791 / 0.003738** |
| P1 单层（TP=2） | **0.004303 / 0.005157** |
| 全 48 层（40% 专家） | 文本连贯，needle **ORANGE-7731** 正确；GPU0 13.9GB |

关键坑（已修）：
- Triton 按**当前设备**启动 ⇒ 必须先 `torch.cuda.set_device(side)`；
- `BK=128` 不整除 TP=2 的 `K=320` ⇒ 越界读 scale（`o` 爆到 7e8）；改 `BK=64` 后正确。

### 4.2 qfn 性能（决定性）

同配置（TP=2、`CPU_OFFLOAD_GB=3`、`EAGER=1`、MAXLEN=512、260+64）：

| 配置 | C=1 |
|---|---|
| 无挎斗基线 | **12.3 tok/s** |
| 全 48 层挎斗 | **5.9 tok/s** |

挎斗内部计时：**8.6–11.3 ms/层**（目标 0.3–0.5ms），48 层 ⇒ 步时 +0.4–0.5s。
批量化只把 4.9→5.9 tok/s ⇒ launch 不是主因，**每层跨设备边界**（`set_device` + 3 次 `.to()` 的隐式同步）才是。

参考：qfn 无挎斗最佳点 `CPU_OFFLOAD_GB=1`：C=1 **68.0 tok/s**，KV 0.41GB（≈512 token）。

### 4.3 ds41f 15K（官方口径重测，2026-10-24）

**口径**：`dsh_15k_v2.jsonl`（md5 `ee65c044…`，32 条/24 会话）、`max_tokens=1024` 自然结束、
每档 16 条、`bench_decode_window.py --tokenizer`（按 token 计数，避免 DSpark 多 token/chunk 低估）、
每档先跑 `2×C` 条预热并丢弃；配置为 README 权威配置（`util 0.70`、`PIN off`、DSpark、无 ASYNC）。

> ⛔ **此前用“数 SSE chunk”的自建脚本得到的 13.2/20.4/24.0 与 15.2/23.7/36.4 已作废**：
> DSH 的 DSpark 一个 chunk 可含多个 token，按 chunk 计数会把 decode 低估数倍。

| C | 无挎斗（window）| 挎斗 1900（window）| 无挎斗（fixed 16 条）| 挎斗（fixed 16 条）| README |
|---|---|---|---|---|---|
| 1 | **68.6** | 11.2 ⚠️ 样本不足 | 43.7 | 43.1 | 42.6 |
| 2 | **70.8** | **76.8** | 62.9 | 50.0 | 69.7 |
| 4 | 79.6 | **106.8** | 73.8 | 69.4 | 72.0 |

- **对照组达到并超过 README**（68.6/70.8/79.6 vs 42.6/69.7/72.0）⇒ 主线没有变慢 ✓
- C=1 挎斗 11.2 是“输出提前自然结束、窗口内仅 135 token”的**样本不足**（§6.1），
  同档 fixed 口径 43.1 vs 43.7，基本持平；
- `fixed 16 条` 含预填竞争（§6.1 已警告），只作参考，不用于扩展性结论。

#### 4.3.1 C=4 复测（2026-10-24，每臂 3 次，同一官方口径）

| 臂 | 窗口 decode（tok/s） | 步时（ms） |
|---|---|---|
| 无挎斗 | 79.6 / 79.0 / 82.0 | 197.4 / 197.5 / 197.6 |
| 挎斗 1900 | **106.8 / 108.5 / 81.1** | 114.1 / 116.7（另一次 115.6）|

**结论：C=4 的 tok/s +34% 不可复现；但“步时 −41%”是真实的引擎收益。**

| 臂 | Mean acceptance length | Avg draft acceptance |
|---|---|---|
| 无挎斗 | 5.15 / 5.09 / 4.66 | **83.0% / 81.9% / 73.3%** |
| 挎斗 1900 | 4.65 / 4.24 / 2.98 | **73.0% / 64.8% / 39.5%** |

- 挎斗**步时稳定低 ~41%**（115.5 vs 197.5 ms 三次均值）⇒ 这是**引擎层的真实收益**；
- **步时收益三次稳定 −41%**（115.5ms vs 197.5ms 三次均值）⇒ 这是可写进 README 的**稳定收益**
  （而 tok/s 会随接受率浮动）；
- 但**DSpark 接受长度同步下降**（5.1 → 4.0，尾部 39.5%），把步时收益抵消成吞吐持平；
- 因此：
  - **步时口径**：挎斗有效（−41%），可作为“引擎更快”的证据；
  - **吞吐口径**：81.1–108.5 vs 79.0–82.0，在噪声内，**不写入 README**；
- 根因假设：GPU0 的 `gpu_moe_decode_fp8` 与 CPU 引擎的**数值路径不一致**（归约顺序/精度/swiglu 限制），
  导致草稿验证命中率下降。要兑现步时收益，必须先做**数值对齐**（fp32 归约、同源 swiglu/量化路径），
  再复测接受率。

## 5. 分析：为什么失败 / 为什么收益有限

1. **逐层跨设备边界的固定成本不可摊薄**
   - 每层要 `set_device`、把 hidden 送 GPU0、把结果收回、再切回；
   - 实测 8.6ms/层，远大于被替代的 Marlin MoE（~0.15ms/层）；
   - 即使 kernel 优化到 0，边界成本仍在毫秒级。

2. **A100 的互联条件不利**
   - GPU0 只有 **PCIe 4.0 x8**（~12.6 GB/s，另两张是 x16）；
   - 任何按层搬运/同步都会被放大。

3. **qfn 的收益是“容量”而不是“速度”**
   - 去掉 1GB offload、把 KV 提到 ~15GB，需要 GPU1/2 少放 40% 专家；
   - 但省下的显存换来的速度收益（68→?）远小于挎斗每层 8.6ms 的损失。

4. **ds41f 的瓶颈是 CPU MoE + SM80 attention**
   - 15K 上下文下 attention 本身很重，挎斗只能分担 MoE；
   - 挎斗的 1900 专家确实降低了 CPU 命中，故 C≥2 有提升；
   - 但绝对吞吐仍受 SM80 执行器代差限制（README 的 42.6/69.7/72.0 是同一硬件上
     官方口径+完整预热的结果，自建脚本没有复现该口径）。

## 6. 建议

| 场景 | 建议 |
|---|---|
| qfn 短上下文 | 维持 `TP=2 + CPU_OFFLOAD_GB=1`：C=1 **68 tok/s**，KV 0.41GB（≈512 token） |
| qfn 长上下文 | **不要用 A100 挎斗**；换 96GB/sm120 级卡（专家 68GB 可全驻留，KV 15GB+） |
| qfn 中等上下文 | `CPU_OFFLOAD_GB=2`：C=1 47 tok/s，KV 1.66GB（≈2K token） |
| ds41f | C≥2 可保留挎斗（+16%~+52%）；C=1 不划算，维持 CPU+GPU1/2 |
| 换卡 | 优先 96GB 级 Blackwell：原生 FP4、无需挎斗、单卡可跑 qfn |

**工程结论**：若未来仍要做跨卡挎斗，必须先解决“每层边界”——
持久 worker/独立 stream/CUDA Graph 把 8.6ms 压到 <0.3ms，否则不要投入。
