## 二、结论：和 xtier 的差距不在"必要浪费"，在一块从没被用起来的缓存

- xtier：单卡 72 GB，热专家 **30 GB**（≈42%）。
- 本项目：双卡 80 GB，热专家 **10.26 GiB**（≈13%）。

差距的**主因不是权重、不是 KV、不是缓冲**，而是：

> 每卡 **11.86 GiB（30%）** 处于 `reserved − allocated` 状态 —— 分配器已经向驱动要下来、
> 但当前没有活张量占用的缓存块。它的来源是启动/预热期一个 **31.29 GiB 的分配峰值**
> （`max_alloc=31.285`），之后 `expandable_segments:True` + 运行期不做 `empty_cache`
> ⇒ 峰值不再回落，稳态只用到 23.59 GiB。

也就是说：**这 11.86 GiB 不是"必须浪费"，而是"闲置着的高水位"**。

## 三、按当前可用量能装多少专家

- 单个专家（FP4，3×5120×1152 / 2）= **8.85 MiB**，实测 8.75 MiB；
- 当前每层 15 槽 ⇒ 40 层 = 5.13 GiB；
- 可用余量 = 缓存 11.86 + 驱动空闲 2.93 = **14.79 GiB/卡**；
- ⇒ 理论上限 ≈ **43 槽/层**，对应每卡 15 GiB、双卡 **30 GiB** —— 正好是 xtier 的量级。

> ⚠️ 前提：增量来自**复用已有缓存块**，因此 nvidia-smi 不应上涨；
> 但缓存块是否连续、KV 池是否被挤压，必须实测，不能只看算式。

## 五、还没算清的一笔（应继续挖）

`max_alloc = 31.29 GiB` 这个峰值是哪一步造成的，目前未知。候选：
权重加载(7.63) + profile 期专家池占位(5.57) + 真缓冲(0.95) + KV(4.58) + 图捕获。
若能把这个峰值压下来（例如让占位与真池复用同一段），`reserved` 会跟着降，
届时可以**既多装专家又保住空闲**，而不是"把缓存填满"。

⇒ 建议在启动流程的关键节点各打一行 `allocated/reserved/max_alloc`（权重后 / 池建后 /
KV 后 / 图捕获后 / 预热后），把峰值定位到具体阶段。这需要改插件（低风险，纯日志）。

## 十三、MTP（dspark）常驻结论：**不值得保留**，但"算在 GPU"没错

### 判断

| 项 | CPU 专家（现状） | GPU 常驻 |
|---|---:|---:|
| dspark 自身 | ~2.6 ms/token（3 层 × 871 µs，B1099–B1106） | **1.5 ms/token**（eager 实测 `[xtu-draft]`） |
| 端到端 tok/s（890p/256out, N=7） | 34.41 | 34.19（+新内核 33.80） |
| 显存代价 | 0 | **+3.36 GiB/卡**，并挤掉 KV 1.75 GiB（4.58→2.83） |

三条臂端到端完全一致（差 <0.5%，噪声内），接受率也没有退化（2.7–3.0）。

### 为什么"更快"却"不值得"

1. **dspark 的 attention/norm/head 一直在 GPU 上算**，从未挪走过；常驻与否只影响它那
   3 层 **MoE 专家权重**的放置。所以"是否值得在 GPU 里算"的答案是**值得**（1.5 vs 2.6 ms）。
2. 但这一步只占一步的 **≈7%**（7.3 ms / 98.3 ms），省 1 ms/token ≈ **1%** 端到端，
   被 91 ms 的验证步完全淹没。
3. 为 1% 付 3.36 GiB，而同样的显存给**目标模型**热专家收益量级完全不同
   （热度实测：top16 覆盖 52–64% 路由、top32 覆盖 74–79%、top64 覆盖 90%）。

### 结论（写进默认值）

- **`XIAOTU_MOE_RESIDENT_DRAFT` 保持默认 0**：dspark 照常在 GPU 上算，专家权重留主机；
- 腾出的 3.36 GiB 归入"可用余量"，优先给目标模型的热专家，而不是 draft；
- B840 那条"GPU 常驻 draft 反而慢一倍"**对 ds41f 不成立**（那是 GLM/k=4 的正确性缺陷产物），
  已在 §十/§十二 用实测更正 —— 但"不快"也意味着**没有理由为它付显存**。

### 附带发现（比结论本身更重要）

`[xtu-draft]` 计时在**非 eager**（FULL_DECODE_ONLY 图回放）下一条都打不出来 ⇒
dspark 整步确实在图里，Python 侧不执行。这同时证明：任何"逐层/逐调用"的活动打点
在图回放下都会失效 —— 所以空闲归还的"活动源"必须挂 `EngineCore.step`（已如此实现）。

## 十六、专家槽位扩展 A/B：**在 A100 上是负收益**（这条把方向钉死了）

同协议（890p / 256out / N=7 / 先预热 / 掐头去尾），只动槽位：

| 配置 | 槽/层 | 专家池 | KV 池 | nvidia-smi | tok/s | 结论 |
|---|---:|---:|---:|---:|---:|---|
| 基线（无自适应） | 15 | 5.13 GiB | 4.58 | 37,445 | **34.41** | 最优 |
| 自适应（窗口 32/64，maxswap 1） | 15 | 5.13 | 4.58 | — | 34.01 | 无变化 |
| **24 槽 + 自适应 + util 0.95** | 24 | 8.40 GiB | **3.25** | 38,655 | **30.81** | **−10%，负收益** |
| 32 槽 + util 0.95 | 32 | 11.21 GiB | — | — | **启动失败** | KV < 1.32 GiB 下限 |

32 槽的失败是**确定性**的、不是 OOM：
```
ValueError: To serve at least one request with the model's max seq len (524288),
1.32 GiB KV cache is needed, which is larger than the available KV cache
```
⇒ KV 有硬下限（一条最长请求），不能为了槽位无限压。

### 为什么多加槽位反而慢（两个可解释项）

1. **KV 被压**：4.58 → 3.25 GiB，前缀缓存容量下降 ⇒ 长 prompt 复用变差；
2. **换入流量**：本轮 `swapped_in` 累计 410 次，换入的 H2D 与 decode 争带宽。

### 为什么 XTier 能靠 50 槽/层快，我们不能（硬件代际）

| | XTier 72 GB | 本项目 2×A100 40 GB |
|---|---|---|
| 槽位 | **50 槽/层**（≈17.5 GiB） | 15 槽/层（5.13 GiB） |
| decode | **141.8 tok/s** | 34.4 tok/s |
| 专家算力 | SM120 **原生 FP4/FP8 张量核** | SM80 **无 FP4/FP8 单元**，专家走 CPU AVX-512 |
| 数据位置 | 专家全在内存（约 81 GiB）+ NVMe 三级 | 专家全在内存（47 GiB），无盘 |

⇒ XTier 把专家搬到 GPU 是"从慢 CPU 搬到极快张量核"，收益一个数量级；
本项目的 CPU 引擎（871 µs/层，全专家常驻内存、无盘）在 A100 上已经很有竞争力，
搬到 GPU（旧 Triton 路径 1272 µs/层）**反而更慢**。这与 B1099–B1106 的微基准完全一致。

**结论：15 槽/层是本机最优；继续加槽是负收益，不再尝试。**

### 用户的"启动期临时用 RAM 扩大 VRAM"思路（记录）

方向正确，XTier 正是用 **CUDA VMM**（预留地址、按需 map/unmap）做到"地址固定、物理页弹性"，
从而能在捕获后继续扩槽而不重捕获。本项目的专家槽是**固定尺寸张量**、地址被 CUDA 图烘焙，
所以要做同样的事必须先**把槽迁到显式 VMM**（我们自己对照文档 §181 的建议 #1）。
但鉴于上面"加槽在本机是负收益"，**这条现在没有做的价值**，除非换卡（有 FP4 单元）。

## 十七、为什么"归还"在持续负载下不会发生（机制级，已定论）

| 触发机制 | 判据 | 实测结果 |
|---|---|---|
| 空闲线程 | 墙钟：距最近一次 forward ≥60 s | 持续流量下永不成立（今天 5 次全部"放弃本轮"） |
| 引擎空闲点 | `EngineCore.step()` 返回后 `scheduler.has_requests()==False` | **一次未触发** —— 日志里"吞吐 0.0"的空闲行只有 **1 行** |

根因：**引擎在无请求时不会进入 `step()`**（阻塞等输入），所以"step 边界 + 无请求"这个
状态本身几乎不存在；有请求时 `has_requests()` 又恒为真。⇒ 两个机制都只能覆盖"真的空闲"。

**推论（必须写进结论）**：
- 那 10.4 GiB 是**会话之间**的收益，**不是持续负载下的收益**；
- dsh 持续打流量时，显存仍是 ~37 GiB（与改造前一致）；
- 想在有流量时也拿到收益，只有一条路：**直接压低启动期高水位**，让 `reserved` 根本不长到 35 GiB。

### 高水位的来源（已有 trace 证据）

实例 541016 的 5 s 采样：profile 后的释放把 `reserved` 打到 22.71 GiB（t=172 s），
之后 **KV 分配 + 图捕获 + 形状预热** 又把它推回 35.45 GiB（t=401 s），而 `allocated` 只有 23.58。
`max_alloc=31.28` 说明峰值由**预热请求的形状**造成，不是稳态需要。

### 下一步（唯一能在有流量时生效的方向）

1. 收缩预热形状（`WARMUP_SCRIPT` 指向 `/home/user/lvllm/stress-run5/warmup_shapes.py` ——
   **注意：该文件在仓库之外，属部署漂移**，要改必须先落进仓库再单向部署）；
2. 或在预热结束、真实流量到来前的空窗里释放一次 —— 但如上所述，引擎在空窗里不跑 step，
   需要外部触发（例如让 `serve_ds41.sh` 在预热收尾时通过受控方式请求一次释放）。

## 十八、定论：那 11 GiB 是**预热高水位**的代价（对照实测）

实例 597355（`WARMUP=0`，其余口径不变）：

| 指标 | 有预热（生产） | **无预热** | 差 |
|---|---:|---:|---:|
| `reserved` | 35.45 GiB | **24.62 GiB** | −10.83 |
| `frag` | 11.86 GiB | **1.48 GiB** | −10.38 |
| nvidia-smi | 37,445 MiB | **26,357 MiB** | −11,088 |
| `allocated` | 23.58 | 23.14 | ≈不变 |
| `free` | 2.48 | **13.75** | +11.27 |

⇒ **高水位 100% 来自形状预热**，不是稳态需要、也不是 KV/专家池。

### 但这不能简单地"关掉预热"

预热覆盖的是 `compile_ranges=32,256,8192` 的编译桶；不做 8192 档预热 ⇒
第一个 8K 级请求要**现场编译**（分钟级停顿）或退回 CPU 预填。这是功能代价，不能默认关。

### 因此结论收敛为一句

> 在**持续有流量**的前提下，这 10.8 GiB 的取舍是：
> **要么** 保留 8K 预热的响应速度，代价是常驻 35 GiB；
> **要么** 不预热 8K 桶，常驻 26 GiB 但首个 8K 请求变慢。
> **两者不可兼得** —— 除非把预热做完后立刻归还（下一步）。

### 下一步（唯一能兼得的路）

让 `serve_ds41.sh` 在预热收尾时**落一个标记文件**，插件侧看到标记且 `frag ≥ 3 GiB`
就做一次归还（`empty_cache` 前再确认无活动）。这样：
- 预热照做（响应速度不变）；
- 预热造成的 10.8 GiB 缓存**在真实流量到来前就还给驱动**；
- 判据是"标记 + 碎片"，不依赖 60 s 空闲窗口（实测该窗口在持续流量下不存在）。

## 十九、成功：预热收尾即归还，**持续负载下也能拿到 10.36 GiB/卡**

实例 601709（`IDLE_EC=1` + 新增的预热收尾触发器）：

```
[xtu-idle-ec] 预热收尾触发器已布防（log=…/ds41_prod_warmup.log）
[xtu-idle-ec] 预热收尾 ⇒ cuda:1 归还 10.36 GiB（reserved 35.02→24.65，free 13.72 GiB）
[xtu-idle-ec] 预热收尾 ⇒ cuda:0 归还 10.36 GiB（…）
nvidia-smi: 37,385 → 26,395 MiB
```

| 检查项 | 结果 |
|---|---|
| 触发时机 | 预热日志出现"完成:"后 2 s 内（无需空闲窗口） |
| 归还量 | **10.36 GiB/卡**（reserved 35.02→24.65） |
| Xid | **12（不变）** |
| `AssertionError` | **0** |
| 归还后真实 chat | `http=200` |
| 同协议 tok/s（890p/256out/N=7） | **35.06**（基线 34.41，**无退化**） |
| 流量后显存 | 28,069 MiB（新流量重新推高一点，符合预期） |

### 为什么这个触发器比前两个可靠

| 触发源 | 可靠性 |
|---|---|
| 空闲线程（墙钟 ≥60 s） | 持续流量下**永不成立**（5 次全部放弃） |
| `EngineCore.step` + 无请求 | 引擎无请求时不跑 step ⇒ **一次未触发** |
| **预热日志收尾** | **每次启动必然发生且只一次** ⇒ 确定性触发 |

### 设计要点（安全）

- 仍受 `XIAOTU_IDLE_EMPTY_CACHE=1` 总开关控制，默认关；
- `frag ≥ 3 GiB` 才动手（预热后的典型值 10.8 GiB）；
- `synchronize` 之后、`empty_cache` 之前**再确认最近 5 s 无活动**，否则放弃；
- 只做一次；异常一律吞掉。

⇒ 至此"那 10.8 GiB 是预热的代价"这条结论被闭环：**预热照做（响应速度不变），
代价在预热结束的瞬间就还给驱动**。

### 长稳第 1 次（实例 604440，修复版）— 2026-11-05 12:43~12:45

| 判据 | 结果 |

## 二十、MBT 与"压住的峰值"的真相（2026-11-05 晚）

### 关键观测：归还的 10.8 GiB 会被**大预填重新吃掉**（这不是浪费，是缓冲）

同一实例连续观测：

| 时刻 | nvidia-smi |
|---|---:|
| 预热收尾归还后 | 26,315 MiB |

| 开始跑 3K/5K/7.5K 词的大预填 | 33,225 MiB |
| 大预填跑完 | **37,805 MiB** |

⇒ 归还的是**缓存**，需要时 torch 会重新向驱动要回来。所以那 10.8 GiB 的真实身份
就是"**峰值缓冲**"，不是"被浪费的空闲"。**稳态**从 37.4 压到 26.3，**峰值没变**。

### MBT 8192 → 中间值有用吗：**没有**

- 激活预算 ≈ **10.8 GiB @ MBT=8192** ⇒ 每 1K token 约 **1.3 GiB**；
- 15K prompt 要单 chunk 必须 MBT ≥ 15K；**任何 8K–15K 之间的值仍然是 2 个 chunk**，
  收益只剩"每 chunk 固定开销"，量级个位数百分比；
- 代价（util 0.9、目标 35.54）：

| MBT | 激活增量 | 落到 KV | 可行性 |
|---|---:|---:|---|
| 8192（现状） | — | 4.58 GiB | 现状 |
| 10240 | +2.7 GiB | ≈1.9 GiB | 勉强可行，但 15K 仍 2 chunk |
| 12288 | +5.4 GiB | <1.32 下限 | 需要动专家池 |
| 16384 | +10.8 GiB | — | **装不下**（总需求 >39.49） |

⇒ **保持 8192**；把余量当峰值缓冲（现状已经如此）。

### 用余量加"上下文"：今天没有收益

`max-model-len` 已是 524288；加余量能加的只是**KV 块数（并发能力）**，
而 KV 池从未被抢占过一次 ⇒ 加了也用不上。

### 想真正"压住峰值"只剩两条路

1. **缩预热形状**（8192 编译桶是峰值来源）—— 代价是首个 8K 请求现场编译；
2. **VMM 弹性池**（XTier 做法）—— 地址预留、物理页按需映射，把峰值也变成按需。

## 二十一、重要更正：TTFT 必须区分"冷启动"与"前缀缓存命中"

先前记录的 TTFT（400 tok 602 ms / 1600 tok 568 ms）**是前缀缓存命中**的结果 ——
测试文本是重复句子、且 salt 在末尾，前缀全部命中，所以数字极低。
把唯一 nonce 放到**提示词最前面**后重新测量（streaming，取两次最小值）：

| words | 估算 tokens | 冷启动 TTFT | 折算 tok/s |
|---:|---:|---:|---:|
| 1,200 | ≈1.6K | **5,961 ms** | 262 |
| 3,000 | ≈3.9K | **12,326 ms** | 316 |
| 6,000 | ≈7.8K | **21,376 ms** | 365 |

引擎侧 `Avg prompt throughput` 会把**缓存命中**的 token 也算进分母，所以日志里看到的
1,246–3,205 tok/s **不能当冷预填速率**；客户端 TTFT 才是真相。

### 这条更正的影响

1. **长 prompt 的 TTFT 主要由预填决定**：按 ≈300 tok/s，15K token 的冷启动约 **40–50 s**；
2. **前缀缓存的收益非常大**（同样 1600 token：5,961 ms → 568 ms，约 10×），
   这也解释了为什么日常对话（有稳定 system prompt / 历史）感觉快；
3. **MBT 的取舍基本被这条否掉**：把 MBT 提到 15K 只能省"每 chunk 固定开销"，
   而预填本身是算力/带宽受限（≈300 tok/s），不是 chunk 数量受限。

⚠️ 今后凡写 TTFT，必须标注是否含前缀缓存命中；两者差一个数量级，混用会得出完全相反的结论。

### 补充：冷预填的准确 token 数（由 `GPU prefill ACTIVE: first N tokens` 给出）

| words | 实际 tokens | TTFT | **折算 tok/s** |
|---:|---:|---:|---:|
| 1,200 | 1,262 | 5,961 ms | **212** |
| 3,000 | 3,155 | 12,326 ms | **256** |
| 6,000 | 6,310 | 21,376 ms | **295** |

（我先前按 1.3 token/词 估算，实际约 **1.05 token/词**。）

### GPU 预填是生效的，但速率只有 ~300 tok/s —— 这是混合推理的固有结果

日志明确：`GPU prefill ACTIVE: first 6310 tokens >= threshold 2560`（阈值 2560 确实被跨越）。
但即便走 GPU 预填，6210 token 仍要 21 s ⇒ **GPU 预填只加速 attention/dense 部分**，
**MoE 专家仍由 CPU 侧计算**（这正是本项目"混合推理"的定义）。

⇒ 结论：
1. 冷预填 ≈ **212–295 tok/s**，随长度略升（固定开销摊薄），**受 CPU MoE 吞吐限制**；
2. 因此 **MBT 提大对冷预填几乎无用**（瓶颈不在 chunk 数），这条彻底关闭；
3. 想提升长 prompt TTFT，唯一的量级手段是**把 MoE 专家搬到 GPU**（受显存与 A100 无 FP4 单元限制，
   已在本轮 §十六 用 A/B 否决）。

## 二十二、**重要限制**：归还是 one-shot，大预填之后不会回落到低水位

实测（长稳实例 622828，13:34 归还后）：

| 时刻 | nvidia-smi |
|---|---:|
| 归还后 | 26,315 MiB |
| 跑 3 轮 890-token 基准 | 28,095 MiB |
| 冷预填 3.1K tok | 35,835 MiB |
| 冷预填 6.3K tok | **37,855 MiB** |
| 再等 2 分钟（无流量） | **37,855 MiB（不回落）** |

根因：归还**只做一次**（`_IDLE_EC_STATE["done"]`），且按审计要求"设了预热触发器就不起空闲线程"
⇒ 之后没有任何再次归还的路径。大预填把缓存重新向驱动要回来之后，就永久留在 allocator 里。

### 影响（必须写进结论）

- **短 prompt / 对话型负载**：收益稳定（26–28 GiB）；
- **含长 prompt 的负载**：第一次 ≥3–4K token 的预填之后，显存回落到改造前的 ~37.8 GiB，
  该实例剩余生命周期内不再受益，**直到重启**。

### 可行的修法（未实施，需审计 + 重启）

把"只做一次"改成"**限次重复**"：允许同一进程内最多 N 次（建议 3–5 次）归还，每次仍要求
`frag ≥ 3 GiB` 且同步后 5 s 内无活动；触发源除了预热收尾，再加"连续空闲 ≥60 s"。
⚠️ 这与历史上 Xid 31 的成因（反复 `empty_cache` + expandable）正面相关，
所以必须**限次**而不是无限制，且每次都要过同一道安全门，并单独跑长稳验证。

### 这是本轮最重要的认知修正

先前把"稳态 26 GB"当作已达成，但那是在**没有长预填**的实例上观测的；
一旦有长预填，收益会消失。验收文档必须把这个边界写清楚，否则使用者会以为"永远省 10 GiB"。

## 二十三、结论修正：运行期"再次归还"没有真实收益 ⇒ **不做 MAX_TIMES**

审计提出的判据：运行期归还只有在三种情况下才有净收益。实测核对本机：

| 可能收益 | 本机事实 | 是否成立 |
|---|---|---|
| (a) 让给同机其它 GPU 进程 | `nvidia-smi --query-compute-apps` 只有我们自己的两个 worker（GPU1/2 各一个）；**GPU0 空闲**且无人使用 | ❌ 无消费者 |
| (b) 给未来更大 batch/新形状留余量 | 与"下次长预填复用这块缓存"**直接冲突**（还掉的正是下次要用的） | ⚠️ 只算安全余量，不算收益 |
| (c) nvidia-smi 好看 | 不是工程收益 | ❌ |

⇒ **`XIAOTU_RELEASE_MAX_TIMES` 不做**。one-shot 是正确形态：
- 启动时把**预热造成的高水位**还掉（那部分确实不会再用到同样的量）；
- 之后长预填把缓存拿回来，就留着给下次长预填用 —— **这才是对的**；
- 反复还掉只会让下次多付一次 `cudaMalloc`，并增加 unmap 次数（Xid 31 的历史成因）。

### 那这次改动的价值到底是什么？（必须诚实回答）

1. **安全余量**：稳态 `free` 从 2.48 GiB 提升到 12–13.8 GiB ⇒ 新形状/异常 batch 的 OOM 风险显著下降；
2. **不再有"长期攥着 11.86 GiB 却永远不用"的缓存**（预热高水位那部分在短 prompt 负载下确实用不到）；
3. **对性能零代价**（tok/s 与 TTFT 均在噪声内）；
4. ⚠️ 但**不是**"随时随地省 10 GiB"：一次 ≥3–4K token 的预填就会把它用掉且不回落。

### 附：审计要求保留的关键证据（不得删）

`26,315 → 28,095 → 35,835 → 37,855 MiB 且不回落` —— 这张表是"归还的是 allocator 缓存、
不改变峰值"的最好证据，也解释了为什么 (b) 类收益不成立。

**不改变峰值**（大预填会重新申请且不回落），因此价值定位是"稳态安全余量 + 消除永不使用的缓存"，
而非"永久省 10 GiB"。draft 常驻显存经三臂实测无收益，已否决。

## 二十六、GPU vs CPU 计算路径：同形状实测（2026-11-05，**推翻前文多处判断**）

### 背景：先修掉一个长期掩盖真相的部署缺陷

1. **线上 `.so` 从未包含内核**：`build_engine_variants.sh` 默认 `BUILD_MOE4=0`，

⇒ 结论：**此前所有"GPU 常驻"臂都没有真正执行过 GPU 内核**，
"GPU 常驻无收益"这一判断缺少实验基础。

### 修复与验证

参数完全一致：H=5120、I=2304、E=384、K=6、GK=32、MXFP4。

## 二十九、更正 §二十七 的显存论断 + 重新定位优化目标（2026-11-05）

§二十七 用"bf16 常驻需 ≈13 GiB"去否定 GPU MoE 优化，**这个论证是错的**：把"权重常驻 bf16"
当成了唯一选项。三条路线的正确账：

| 路线 | 显存增量 | 每层流量 | 预估 |
|---|---:|---|---:|
| (a) bf16 权重常驻 | **+13 GiB** | 537 MiB 读 | 734 µs（实测） |
| (b) 动态反量化到 scratch + cuBLAS | ~0.5 GiB | 137 读 + 537 写 + 537 读 = 1.2 GiB | ~1.2 ms（**更慢**） |
| (c) **融合反量化+GEMM** | **0**（权重仍 4-bit） | **137 MiB 读** | 下限 137 µs，现实 200–400 µs |

⇒ **(b) 才是费带宽的那种**；**(c) 不占额外显存**。

### 更关键的实测反差

同一张卡、同一形状：现有 `moe4_smallm` 跑 **127 GB/s**，cuBLAS bf16 跑 **723 GB/s**
⇒ **近 6 倍差距来自访存模式，不是缺张量核**。生产形状每层只需读 137 MiB：

- 127 GB/s ⇒ 1067 µs（现状）
- 700 GB/s ⇒ **≈196 µs**
- 1 TB/s ⇒ 137 µs

⇒ 修正后的目标：**先修访存（16B 向量化、去掉每 nibble 一次 LUT、提高占用率），
不必上张量核**；draft 3 层 3.2 ms → ~0.7 ms，步时省 **≈2.5%**（刚过 2% 门）。

## 三十、融合反量化 + tensor core 原型实测（2026-11-05 傍晚）

按"反量化 + tensor core"实现 wmma 原型（`/tmp/mma/full.py`，权重始终 MXFP4，进 shared 展成 bf16 再 mma）：

| 项目 | 结果 |
|---|---|
| 数值（合成权重 vs fp64） | **4.4e-07**（门限 1e-5 ✅） |
| 生产形状每层（K=5120 N=2304 15 专家） | **1.58 ms**（52 GB/s） |
| 同结构但权重直读 bf16（跳过解包） | **1.147 ms** |
| 生产标量内核 `moe4_smallm` | **1.067 ms** |
| 隔离 GEMV 探针（同访存，无 MoE 结构） | **0.122 ms**（747 GB/s） |
| 纯读上限 | 0.077 ms（1182 GB/s） |

### 三条实测结论

1. **wmma 版没有赢**：1.58 ms > 标量 1.067 ms。原因是 wmma 每次 mma 都要
   `load_matrix_sync`（shared 往返）+ 16 行补齐（M=5 只用 5/16 行）。
2. **解包不是主因**：跳过解包的 bf16 直读仍要 1.147 ms ⇒ **结构开销**（shared 往返、小 tile、同步）
   才是主因。真正的 marlin 式做法（寄存器里直接拼 B 片段 + raw `mma.m16n8k16`）才能绕开。
3. ⭐ **最值钱的是"结构税"**：隔离 GEMV 探针 0.122 ms vs 生产内核 1.067 ms，
   同样数据量差 **8.7×** ⇒ MoE 结构（分段/8-token 累加/原子/槽位间接）是当前最大的一块。

### 下一步（按性价比排序）

1. 把"结构税"逐项拆掉：X 先搬 shared（现在每 j 为 8 个 token 各做 2 次全局加载 = 16 次换 1 次有效读）；
2. 去原子：一个 block 负责一个 (专家, 输出块) 的完整 K 归约，消除 split-K 原子；
3. 上述两条做完再评估是否还需要 raw-mma 版本。

| 尝试 | 结果 | 原因 |
|---|---|---|
| 双缓冲（sB ping-pong） | 1.062 ms（更差） | 预取与 mma 由同一批线程串行发出，没有 `cp.async` 就无法重叠 |
| TPW=2（每 warp 两个输出 tile） | 15 专家 1.028 ms（更差）；30 专家 1.006 ms（更好） | 块数不足时并行度受限；只在专家多时受益 |
| KC=128 / KC=32 | 1.614 / 1.061 ms（都更差） | KC=64 是当前最优点 |

### 硬件属性核查（排除两类常见怀疑）

`-Xptxas -v`：**0 spill**、54 寄存器、10 KB shared ⇒ 占用率约 56%（9 块/SM）。
⇒ 不是寄存器溢出、也不是占用率不足；瓶颈在**每段的结构开销**（sB staging + 同步）。

### 排序判据的现状（仍未通过）

- 本内核 **gate_up 单段** 30 专家 = 1.054 ms；
- CPU 引擎 **整层（gu+dn+SwiGLU）** = 1.14 ms；
- 由于 dn 与 gu 体量相当，本内核补齐 dn 后约 **2.1 ms** ⇒ 仍慢于 CPU **约 1.8×**。
⇒ 排序判据**仍不通过**；下一步必须去掉 sB staging（raw `mma.m16n8k16` + 寄存器内拼 B 片段）。

## 三十四、第 4 轮：wmma 路线到顶（0.727 ms），确认必须换 raw mma

| 尝试（都在 v8 基础上） | 15 专家 | 结论 |
|---|---:|---|
| v8 基线（A 走 global、单缓冲） | **0.727 ms** | 最优 |
| v9 双缓冲（buf 索引交替） | 0.749 ms | 无收益：没有 `cp.async`，预取无法与前一轮 mma 重叠 |

### 判定：wmma 这条路已到顶

- 0.727 ms / 84 MiB ⇒ 113 GB/s，等效 **1.22 TFLOP/s**；GPU 峰值 312 TFLOP/s ⇒ 仍只有 0.4%；
- 排除项已逐个实测：无 spill、占用率 56%、KC 最优点 64、TPW/KC/双缓冲都不再有收益；
- 剩余开销就是「B 片段必须经 shared 往返一次 + `__syncthreads`」这个 wmma 的固有形态。

⇒ 下一步（第 5 轮起）：**raw `mma.m16n8k16` + 寄存器内直接拼 B 片段**，删掉 sB 与全部 block 级同步。

### 已经查清的 raw-mma 映射（省得下一轮重新推）

`mma.sync.aligned.m16n8k16.row.col.f32.bf16.bf16.f32`，线程 t（0..31）：

| 操作数 | 每线程持有 | 位置 |
|---|---|---|
| A（16×16，row-major） | 8 个 bf16 | 行 t/4 与 t/4+8；列 (t%4)*2 +{0,1} 与 +{8,9} |
| B（16×8，col-major） | 4 个 bf16 | 列 n = t/4；行 (t%4)*2 +{0,1} 与 +{8,9} |
| C（16×8，f32） | 4 个 float | 行 t/4 与 t/4+8；列 (t%4)*2 +{0,1} |

MXFP4 对应关系：`B[k][n] = deq(nibble) * 2^(scale[k/32][n]-127)`；
行 (t%4)*2 与 +1 是 `W[(t%4)][n]` 的低/高 nibble，行 +8/+9 是 `W[(t%4)+4][n]` 的低/高 nibble
⇒ **每个线程每个 k-tile 只需读 2 个字节**，且同一 32-k 组内 scale 恒定 ⇒ 每线程只需 1 次 scale 读取。

## 三十五、第 5 轮：raw `mma.m16n8k16` 跑通（数值对，但慢在访存）

### 结果

| 实现 | 每层（15 专家） | 带宽 | 算力 | 数值 |
|---|---:|---:|---:|---:|
| wmma v8（最优） | **0.727 ms** | 113 GB/s | 1.22 TFLOP/s | 4e-07 |
| **raw mma（本轮）** | 1.891 ms | 44 GB/s | 0.47 TFLOP/s | 3.99e-06 |

⇒ raw mma **数值正确**（B 片段在寄存器里直接由 MXFP4 拼出，无 shared、无 block 同步），
但**更慢**。原因已定位：每个线程每个 k-tile 只读 **2 个字节**，一个 warp 变成 32 次单字节加载
⇒ 全局访存完全非合并，44 GB/s。

### 正确改法（下一轮）

marlin 的真实形态不是"寄存器直读全局"，而是：

1. **只把原始 4-bit 字节搬进 shared**（`sW[KC/2][NTILE]`，KC=64 时仅 2 KB/段），
   全局加载可以 16 字节合并；
2. 各线程从 shared 取自己需要的 2 个字节（`sW[k/2][n]`、`sW[(k/2)+4][n]`），
   在**寄存器里**解包 + 乘 scale，再喂 raw mma。

⇒ 相比 v8 的"把 bf16 写进 shared"，shared 流量从 4 倍降到 1 倍（84 MiB 而不是 336 MiB），
且保留了 raw mma "无 bf16 staging" 的优点。

### 精度说明

raw 版 3.99e-06 / 5.28e-06（两次），比 wmma 版 4e-07 差一个量级但仍在 1e-5 门限内。
来源是 bf16 里乘 scale 的舍入（每元素 ~2^-9，5120 项随机符号平均后 ~3e-5 量级）。
若后续要更严的门限，可改为一组内不乘 scale、而在每组结束时乘到累加器（需 2 组累加器）。

## 三十六、第 6 轮：marlin 形态（4-bit 字节进 shared）1.089→1.039 ms，仍不及 wmma

| 实现 | 每层（15 专家） | 带宽 | 算力 | 数值 |
|---|---:|---:|---:|---:|
| **wmma v8（仍最优）** | **0.727 ms** | 113 GB/s | 1.22 TFLOP/s | 4e-07 |
| raw mma（全局单字节） | 1.891 ms | 44 GB/s | 0.47 TFLOP/s | 3.99e-06 |
| **marlin 形态 v1**（4-bit 字节进 shared，每 warp 2 tile） | 1.089 ms | 76 GB/s | 0.81 TFLOP/s | 5.30e-06 |
| marlin 形态 v2（每 warp 4 tile，复用 A） | 1.039 ms | 79 GB/s | 0.85 TFLOP/s | 4.12e-06 |

### 为什么 raw mma 没赢（两条实测归因）

1. **A 片段流量被放大**：每线程每 k-tile 读 16 字节 A，而 B 只有 4 字节；且每个 block 重复读同一份 A
   ⇒ 15 专家 × 36 个 N-块 × 160 KB ≈ 86 MB，与权重（84 MB）相当 ⇒ **总访存翻倍**。
   把每 warp 的 tile 数从 2 加到 4（复用 A）只回收了 5%（1.089→1.039）。
2. **B 片段构造是标量活**：每线程每 k-tile 要 2 次 shared 字节读 + 4 次 `e2m1_bits` +
   4 次 bmul + 2 次打包（20+ 指令）才换 2 个有效字节；
   而 wmma 的 `ldmatrix` 一条指令搬 8 个 bf16 ⇒ **手写版的"组装成本"高一个量级**。

⇒ 结论：**不做 `ldmatrix`/shuffle 级别的向量化，raw mma 打不过 wmma**。
下一步要么补上 shuffle 向量化（工作量大），要么接受 wmma v8 = 0.727 ms 为当前最优，
把力气转到"补齐 down 投影 + SwiGLU，做完整层的排序复核"（验收项 3 尚未闭环）。

### 遗留的未解释差距（诚实记录）

wmma v8 的 0.727 ms 比"指令数估算"的 ~40 µs 高 18 倍，且：无 spill、占用率 56%、
KC/TPW/双缓冲都试过无改善。没有 ncu 的情况下该差距尚未定位，**不作为已解释结论**。

## 三十七、第 7 轮：shared bank 冲突是真凶之一（+34%）

### 突破

| 版本 | 15 专家/层 | 带宽 | 说明 |
|---|---:|---:|---|
| v8（上轮最优） | 0.727 ms | 113 GB/s | `sB[KC][NTILE]`，行跨 64 元素 = 128 B |
| **v10（本轮）** | **0.543 ms** | **152 GB/s** | **`sB[KC][NTILE+8]`，行跨 72 元素 = 144 B** |

⇒ 行跨是 128 B 时，同一 warp 的多行写到相同的 bank 组 ⇒ 严重冲突；加 8 个元素（16 B）打散后**−25%**。
数值仍正确（合成 6.16e-07 / 真实 6.62e-07）。

⇒ 仍差 CPU **3.6×**、差纯读下限 **6.5×**；排序判据（GPU 最快）**尚未通过**。

### 累计优化曲线（同形状，15 专家/层）

## 三十八、第 8 轮：scale 处理是 35% 开销；并确立"重复取中位"的测量方法

### 消融（同形状，15 专家）

| 配置 | 每层 | 说明 |
|---|---:|---|
| 带 scale | 0.525 ms | |
| **无 scale** | **0.341 ms** | ⇒ **scale 处理占 0.184 ms = 35%** |

根因：旧实现用 `exp2f(byte-127)` + 逐元素 bf16→float→bf16 转换（每个 16B 块 16 次 exp2f + 32 次转换）。

### 优化（v11）

1. `2^(s-127)` 在 bf16 里就是指数位 ⇒ 直接 `s << 7`，**不需要 exp2f**；
2. 用 `__hmul2` 一次乘两列（bf16 硬件乘法），替代逐元素 float 转换。

### A/B 结果（各跑 3 次取中位）

| 版本 | 3 次 | 中位 |
|---|---|---:|
| v10（pad + exp2f） | 0.714 / 0.559 / 0.702 | 0.702 ms |
| **v11（pad + 位移 scale + hmul2）** | 0.579 / 0.553 / 0.649 | **0.579 ms** |

⇒ **−17%**。

### ⚠️ 方法教训（重要，影响此前所有数字）

单次测量的**方差高达 ±25%**（同一份代码三次跑出 0.553/0.579/0.649，甚至 0.714）。
⇒ 从本轮起：**任何内核性能结论必须 ≥3 次重复取中位**，单次读数只能作参考。
⚠️ 这也意味着本账本此前记录的若干"小幅改善"（例如 0.985 vs 0.948 这类 4% 差异）
**可能落在噪声范围内**，不应作为已确立的结论；只有幅度 ≥15% 的改动才算可信
（如 bank pad −25%、scale 优化 −17%）。

### 当前最优（v11）

- 15 专家/层：**0.579 ms 中位**（约 145 GB/s）；
- 30 专家/层：0.855 ms（193 GB/s）；
- 数值：合成 4.87e-07 / 真实权重 2.88e-07。

## 三十九、第 9 轮：整层打通（gu + SwiGLU + dn），0.948 ms

### 实现

内核加了 `Astride`（A 的专家跨距）：`Astride=0` 时各专家共享同一份激活（gate_up），
`Astride=16*K` 时按专家取各自的激活（down，每个专家的输入不同）。

⇒ **down 从 15 次 kernel launch 合并为 1 次**：整层 1.604 → **0.948 ms**。

### 整层数值（对 fp64）

| 段 | 相对误差 |
|---|---:|
| gate_up | **5.02e-06** |
| down（含 SwiGLU 中间量） | **1.45e-06** |
| 合成单段 / 真实权重单段 | 3.90e-07 / 2.79e-07 |

⇒ 全部在 1e-5 门限内。

### 三行对照（整层，15 专家/层，per-rank）

| 项 | 每层 | 流量 | 有效带宽 |
|---|---:|---:|---:|
| **本内核（gu+dn，含 SwiGLU）** | **0.948 ms** | 127 MiB | **130 GB/s** |
| 标量内核 `moe4_smallm`（仅 gu） | 1.067 ms | 84 MiB | 127 GB/s |
| 纯读下限（127 MiB @1 TB/s） | 0.127 ms | — | 1000 GB/s |

### ⭐ 排序判据：仍不通过（但把口径讲清楚）

| 路径 | 工作量 | 每层 | 有效带宽 |
|---|---:|---:|---:|
| 本内核（GPU，15 专家） | 127 MiB | 0.948 ms | 130 GB/s |
| CPU 引擎（BS=6，约 35 个不同专家，world=1 即 2× 分片） | 620 MB | 1.14 ms | **≈544 GB/s** |

⇒ 墙上时间上 GPU 略快（0.948 vs 1.14 ms），但**CPU 做了 4.9 倍的工作量**；
按单位工作量的带宽衡量，**GPU 只有 CPU 的 1/4.2** ⇒ 排序判据（纯 GPU 最快）**不通过**。

⚠️ 口径说明：这两个数字的专家数与分片大小不同（GPU 15 专家/per-rank，CPU ~35 专家/全分片），
因此**不能直接用墙上时间下结论**；用"有效带宽"比较才是同口径的。要真正同口径复核，
需要让 CPU 引擎按 `top_k=3 / 5 token / 15 专家` 跑一次（下一轮补）。

### 累计（同形状 15 专家）

gu 单段：3.317 → … → 0.579 ms 中位（v11）
整层（gu+SwiGLU+dn）：1.604 → **0.948 ms**（v13）

## 四十、第 10 轮：同口径对照 + **更正此前所有 TFLOP/s 数字**

### ⚠️ 先更正一个错误（影响 §三十一~§三十九）

此前 GPU 的"等效算力"是按 `专家数 × token 数 × K × N` 算的，**多算了约 5 倍**；
真实的有效工作量应按**专家-token 对数**（每个 token 只被 topk 个专家计算）计算。

| 段 | 正确的每对 FLOPs（per-rank） |
|---|---:|
| gate_up | 5120 × 2304 × 2 = 23.6 MFLOP |
| down | 1152 × 5120 × 2 = 11.8 MFLOP |

⇒ **整层 15 对 = 531 MFLOP**，本内核 0.948 ms ⇒ **0.56 TFLOP/s**（此前误报为 1.27）。

### 同口径对照（都用 15 个不同专家、5 个 token）

| 路径 | 专家数 | token | 每层 | 有效带宽 | **有效算力** |
|---|---:|---:|---:|---:|---:|
| **CPU 引擎**（`DEDUP=15`，全分片 I=2304，topk=6） | 15 | 5 | **0.61 ms** | **435 GB/s** | **3.47 TFLOP/s** |
| **本内核**（per-rank I=1152，topk=3） | 15 | 5 | **0.948 ms** | **140 GB/s** | **0.56 TFLOP/s** |
| A100 bf16 峰值 | — | — | — | 1550 GB/s | 312 TFLOP/s |

⇒ **GPU 单位算力比 CPU 慢 6.2 倍，单位带宽慢 3.1 倍**；只用到 GPU 峰值的 **0.18%**。

### ⭐ 排序判据结论（明确）

**不通过。** 同口径下"纯 GPU 驻留"反而比"纯 CPU"慢 6 倍；按用户定的判据，
这证明**实现仍有严重问题**，而不是硬件不行 —— 与"GPU 峰值是 CPU 的 ~90 倍"这一事实直接矛盾。

### 仍未定位的部分

已排除：spill（0）、占用率（56%）、shared bank 冲突（已修，−25%）、scale 处理（已修，−17%）、
KC/TPW/unroll/双缓冲（均无益）。剩余 ~6 倍差距**尚未定位**，需要 ncu（本机无）或更细的消融。

## 四十一、第 11 轮：na 扫描定性 —— 固定开销受限，不是计算受限

### 实验（同形状，15 专家，只改 token 数）

| na（token 数） | 每层 |
|---:|---:|
| 1 | 0.535 ms |
| 2 | 0.403 ms |
| 5 | 0.393 ms |
| 8 | 0.395 ms |

⇒ **na=2..8 时间几乎不变**（0.393–0.403 ms）。这说明内核的时间由**每字节的固定处理成本**
决定（解包 + 写 shared），而不是由 token 数（计算量）决定 ⇒ **不是计算受限**。

### 由此得到的定量结论

| 项 | 每层 | 说明 |
|---|---:|---|
| 纯读同样 84 MiB | 0.077 ms | 1182 GB/s（此前的 K2 探针） |
| **本内核（无 scale）** | 0.341 ms | ⇒ 解包+写 shared 占 **0.264 ms（4.4×）** |
| 本内核（带 scale，v11） | 0.579 ms 中位 | |

⇒ 剩余 5 倍差距**全部在"MXFP4→bf16 解包并写入 shared"这条固定路径**上，
与 token 数、与 mma 都无关。

### 已排除的解释

- **不是 N-slab 跨步访存**：此前的 K2 纯读探针用的是同样的跨步模式（每行 64 B），
  仍跑到 1182 GB/s ⇒ 访存模式本身没问题；
- **不是指令数**：按 13 ops/字节估，84 MiB 只需约 55 µs，实测 264 µs；
- **不是占用率**：9 块/SM、56%、无 spill。

⇒ 剩下的解释只能是"每段只有 1 次加载 + 2 次同步"导致的**延迟未被掩盖**。
下一轮做定向实验：`__launch_bounds__` 提高占用率、每线程每段 2 次独立加载、
以及把 KC 与块大小配对调整，看能否把 264 µs 压到 100 µs 以内。

## 四十二、第 12 轮：孤立路径与整内核的差距不传递（重要方法结论）

### 孤立探针：解包 + 写 shared（无 mma、无同步）

| 实现 | 每层 | 等效带宽 |
|---|---:|---:|
| 逐 nibble 位运算 | **0.400 ms** | 221 GB/s |
| **shared 256 项字节表** | **0.164 ms** | **538 GB/s** |

⇒ 孤立路径上，查表比位运算快 **2.4 倍**。

### 移植到整内核后：收益消失

| 版本（A/B 各 3 次取中位） | 3 次 | 中位 |
|---|---|---:|
| v11 位运算 | 0.537 / 0.649 / 0.617 | 0.617 ms |
| v14 shared LUT | 0.591 / 0.645 / 0.504 | 0.591 ms |

⇒ 只差 **4%，落在 ±25% 噪声内**。

### 结论（值得记住的方法论）

**孤立探针上的优化，不一定传递到整内核** —— 因为整内核里解包、mmmma、同步是
**时间上重叠/耦合**的：解包快了，等待 shared 写入与同步的那部分就顶上来了。
⇒ 后续任何优化都必须**在整内核上做 A/B（≥3 次）**，孤立探针只能用来判断"某一侧有没有余量"。

### 连带发现：之前的 na 扫描结论需要限定

§四十一 由"na=2..8 时间不变"推出"固定开销受限"仍成立，但**不能**据此认定
"解包就是全部成本"——因为整内核对解包提速 2.4 倍无响应，说明还有别的固定成本（同步/共享读）。

## 四十三、第 13 轮：**拿到 profiler（ncu）**，瓶颈首次被定量定位

| 指标 | 值 | 含义 |
|---|---:|---|
| Duration | 704 µs | |

| Compute (SM) | 55.0% | |
| **Achieved Occupancy** | **26.2%** | 偏低（此前按寄存器估算是 56%，实际只有一半） |
| Mem Busy / Max Bandwidth | 64.7% / 31.7% | 管线忙但只搬了 1/3 峰值 ⇒ 访存效率差 |
| Executed IPC | 1.79 | |

### ncu 给出的两条可执行诊断

1. **全局访存未合并：45% 的 sector 是多余的**（13.8M / 30.5M）；
   最可能来源：`load_matrix_sync(fa, A + k0 + kk, K)` 每次从 global 取 16 行 × 32 B（跨步 K）
   ⇒ 每次只用掉 128 B 行里的 32 B。
2. **shared 访存未合并：33% 的 wavefront 多余**（2.76M / 8.29M）；
   来源：每线程写 2×16 B 到同一行，4 个线程覆盖 128 B 但用 8 个 wavefront。

### 下一步（有依据，不再靠猜）

1. 把 A tile 用**合并方式拷进 shared**（16×KC = 2 KB），再由 `ldmatrix` 取；
   预计消掉 45% 的全局冗余 sector；
2. 调整 sB 的写入映射（每线程 8 列、写 16 B×2），把 shared wavefront 从 8 降到 4；
3. 提高占用率（26% → 40%+）：减小 shared 占用或调整块大小。

⚠️ 注意：v7 曾试过"A 进 shared"（0.948 ms，比 v8 的 0.727 慢），但那次是在
**未修 bank pad、未修 scale、未加 LUT** 的旧结构上测的，且当时没有 profiler；
现在有 ncu 指向"45% 全局冗余"，值得在**当前结构**上重做一次并 A/B。

## 四十四、第 14 轮：三个方向都是负结果；占用率 26% 的真实原因被解释清楚

### 尝试与结果（均 ≥3 次或直接可见的差异）

| 改动 | 结果 | 结论 |
|---|---|---|
| A tile 合并拷进 shared | 0.716 ms vs 基线 0.711 ms | **无收益** |
| TPW=4（每专家 9 个块，A 复用 4 倍） | 0.945 / 1.069 / 1.140 ms | **明显更差**（并行度不足） |
| K 方向切分（+原子累加，KSPLIT=4/8） | `unspecified launch failure` | **未跑通**，原因未定位 |

### ⭐ 关键解释：A 的流量问题不在"未合并"

A 的合并拷贝没有收益，因为 A 的浪费**不是访存模式**，而是**被重复读**：
每个专家有 36 个 N 块，每块都把整段 A（16×K）读一遍 ⇒ A 总流量 88 MB，与权重（84 MB）相当。
ncu 报的"45% 冗余 sector"确实是问题，但修它只能减少每块的 sector 数，不能减少块数。

### ⭐ 占用率 26% 的正确解释

不是寄存器或 shared 限制（两者都允许 9 块/SM），而是**网格太小**：
540 个块 / 108 SM = **5 块/SM**，5×4 warps = 20 warps，占 64 warp 上限的 **31%**（实测 26%）。
⇒ 提高占用率的唯一路径是**增加块数**（K 切分是正解），而 TPW 越大块数越少 ⇒ 越差，
这正好解释了 TPW=4 的失败。

### 下一步

把 K 切分做对（当前实现有 bug：`unspecified launch failure`）。
怀疑点：`store_matrix_sync` 到栈上临时缓冲后再原子累加这条路径；
更稳的做法是**用共享内存做临时缓冲**，或改成"每个 K 段写自己的 partial 缓冲 + 单独的归约 kernel"。

## 四十八、第 18 轮：每块 2 专家（省 A 流量）未跑通，记录两个已知 bug

### 动机（有依据）

A 的总流量 = 每专家 36 个块 × 16×K × 2 B ≈ **86 MB**，与权重 84 MB 相当 ⇒ 总访存接近翻倍。
让一个块同时处理 2 个专家，A 只读一次即可摊到两个专家 ⇒ 理论可省 ~25% 总流量。

### 结果：失败，两个 bug

1. **奇数专家越界**（已修）：NE=15 时最后一个块会去算不存在的第 15 号专家 ⇒ 非法访存；
   加 `nE = (e0+1 < NE) ? 2 : 1` 保护后仍崩。
2. **`Sce` 未按专家偏移**（未修）：只把 `We` 按 `ee*(K/2)*N` 偏移了，
   但 `Sce` 仍是专家 e0 的基址 ⇒ 第二个专家会读到别人的 scale（即使不崩，数值也是错的）。

⇒ 该版本**未跑通**，本轮不采纳；当前最优仍为 **v20 / KSPLIT=12 = 0.372 ms**。

### 教训

"每块多专家"改的是**内核的数据流**（A 摊薄 + 双份 sB + 双份累加器），
不是参数级改动；本轮在未做完整边界/偏移审查的情况下就上机，
导致两轮时间花在崩溃定位上。⇒ 这类改动应先写清"每个指针的专家偏移"清单再动手。

## 五十一、第 21 轮：raw 字节 + 寄存器解包 + raw mma 重做（带 LUT/KSPLIT/pad）——仍差一倍

### 动机（ncu 依据）

shared 流量 = 输入字节的 8 倍（写 4× + ldmatrix 读 4×），且 Mem Busy 84%。
只放**原始 4-bit 字节**可把 shared 流量降到 2×（写 1× + 字节读 1×），并彻底去掉 ldmatrix。

### 实现

`sW[KC/2][NT+PAD]` 存原始字节（合并 16B 加载），每线程从 shared 取 **2 字节**，
用 shared LUT 解包成 4 个 bf16（2 个 packed uint32），再发 `mma.sync.aligned.m16n8k16`。
带 K 切分（原子累加）、pad=16、LUT、A 从 global 取。

### 数值：正确

| ksplit | 相对误差 |
|---:|---:|
| 1 | 5.33e-06 |
| 4 | **9.25e-07** |

### 性能：仍差一倍

| 实现 | 每层（15 专家） | 带宽 |
|---|---:|---:|
| **wmma + bf16 进 shared（v20）** | **0.372 ms** | **226 GB/s** |
| raw 字节 + raw mma（ksplit=1） | 1.106 ms | 74 GB/s |
| raw 字节 + raw mma（ksplit=4） | 0.761 ms | 108 GB/s |
| raw 字节 + raw mma（ksplit=12） | 0.763 ms | 108 GB/s |

⇒ **shared 流量降到 1/4 并没有换来提速**，反而慢一倍。

### 结论（这条分支可以关闭了）

减少 shared 流量不是当前的主要矛盾。raw mma 的代价是：
1. 每线程每个 k-tile 要做 2 次字节读 + 2 次 LUT + 4 次打包 + 2 次 hmul2，才换 **1 个 mma**；
   而 wmma 的 `ldmatrix` + `mma_sync` 一条指令就处理 8 个 bf16，指令效率高一个量级；
2. 字节级 shared 读天然有 bank 冲突（8 个线程读 8 个连续字节只落在 2 个 bank）。

⇒ **wmma + bf16 进 shared + LUT + KSPLIT（0.372 ms）仍是唯一正确的主线**；
后续应在**同一结构**内继续压（例如减少每字节指令、提高 ldmatrix 效率），不再走 raw mma。

### ⚠️ 抓到一个假速度（值得记的方法论案例）

### TPW=4 仍编译失败

加 `__launch_bounds__(128, 6)` 后 nvcc 仍返回 255（寄存器/段溢出）。

若要继续走"提高 A 复用"，需要先减寄存器：把解包暂存从 lo/hi 数组改成直接写 shared（不经过数组），

- 下一步优先试**减少解包阶段的寄存器占用**（让 TPW=4 能编译），
  或者**把 A 片段在 k 循环外预取到寄存器数组**（每 warp 只保留当前 k-tile 的 A）。

## 六十、第 30 轮：TPW=4 被 shared 上限判死；确认 TPW=2 为最优

### TPW=4 失败的真实原因（不是我上一轮猜的寄存器）

`NTILE = 16×4×4 = 256` ⇒ 静态 shared：
`sB 64×264×2 = 33.8 KB` + `sC 16×256×4 = 16 KB` + `sA 2.3 KB` + `lut 1 KB` ≈ **53 KB > 48 KB**
（sm_80 的**静态** shared 上限是 48 KB，动态才可以申请到 100 KB）⇒ ptxas 直接报错。

### 验证：把 sC 去掉后 TPW=4 能编译，但更慢

| 配置 | 每层 |
|---|---:|
| TPW=1，KSPLIT=1 | 0.385 ms |
| **TPW=4，KSPLIT=1（sC 去掉）** | **0.541 ms** |

⇒ TPW=4 只能在 KSPLIT=1 下跑（否则 shared 超限），而 KSPLIT=1 本身就慢，
**两者无法兼得** ⇒ TPW=4 这条分支关闭。

### 结论

**最优配置 = TPW=2 + KSPLIT=12 + pad=8 + KC=64 + shared LUT**：
gu 单段 0.275 ms、整层 0.456 ms、数值 5.33e-06 / 1.63e-06。

### 已经系统排除的方向（不再重复）

| 方向 | 结论 |
|---|---|
| 减 shared 流量（raw 字节 + raw mma） | 慢一倍（§五十一） |
| 每块 2 专家（摊薄 A） | 慢 15–35%（§五十二） |
| union 复用 sB/sC | 加一次同步，慢 20%（§五十四） |
| 提高占用率（8 warps / 减 sA） | 无收益或更差 |
| TPW=4 | shared 超限，且单独跑更慢 |
| pad / KC / KSPLIT 扫描 | 已到平台 |
| 原子累加开销 | 实测为 0 |
| 每块固定开销 | 实测无关 |
| 每段同步 | 实测仅 7 µs |

### 下一步（唯一还有理论空间的方向）

**双缓冲，让 staging（0.115 ms）与 mma（0.18 ms）重叠** —— 当前二者是串行的（0.296 ≈ 0.115 + 0.18）。
若重叠成功，理论上限约 0.18–0.20 ms，比当前再快 30–40%，并且能首次把 gu 打进 0.2 ms 以内
（对应 >440 GB/s，接近 CPU 的 449 GB/s）。

每 SM 的块数从 ~5 掉到 ~2.8，占用率下降的代价超过重叠收益。
